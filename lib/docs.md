# Noridoc: lib

Path: @/lib

### Overview

Framework-agnostic data and utility modules: the canonical `Product` types, the static in-repo catalog (copy and line-sheet prices) joined to a committed snapshot of the Shopify store for purchasable variants, the generated image manifests, the editorial photo constants (landing hero, newsletter picture) plus one generated lookbook manifest per collection season — folded into the ordered `SEASONS` list — with the stacking and column-balancing helpers, the server-only Shopify Admin API client used by the checkout route, the `CheckoutInfo` type, price formatting, and the shared form field validators. No React components live here.

### How it fits into the larger codebase

Pages in @/app call `getProducts`/`getProduct` from @/lib/catalog.ts; components and the cart use `formatPrice` and the types in @/lib/product.ts; @/components/CheckoutFlow.tsx imports only the `CheckoutInfo` type from @/lib/checkout.ts; @/app/api/checkout/route.ts is the sole importer of @/lib/shopify-admin.ts; @/app/page.tsx, the two collections routes (@/app/collections/page.tsx, @/app/collections/[season]/page.tsx), @/components/SeasonTabs.tsx, and @/components/NewsletterModal.tsx consume @/lib/gallery.ts; the three forms in @/components consume @/lib/validation.ts. The generated files are written by scripts and read here: @/lib/looks.json by @/scripts/import-looks.mjs (read only by the catalog), @/lib/lookbook.json and @/lib/lookbook-season-1.json by @/scripts/import-lookbook.mjs (one run per season, read only by @/lib/gallery.ts), and @/lib/shopify-products.json by @/scripts/sync-shopify.mjs (read only by the catalog, through `matchToCatalog` and `orderVariants` in @/lib/shopify-products.ts). Shopify is reached only through its Admin API with the client-credentials grant, offline by the sync script and at runtime by @/lib/shopify-admin.ts; there is no public storefront fetch and no cart permalink.

### Core Implementation

- @/lib/product.ts — `Product`, `ProductVariant` (`{ id, size, price, available }`), `ProductDetailGroup`. `price` is optional (UI hides it when undefined); `sizes` is a display-only string from the line sheet (e.g. `44, 46, 48 EU`); `details` is a list of `{ heading, items }` groups ("Styling Details", "Materials and Product Care"); `variants` may be empty.
- @/lib/catalog.ts — a `LOOKS` array of hand-edited copy (title, sizes, description, details) and a numeric `price` transcribed from the brand's "Website 2.0 Outline" line sheet, one entry per studio look. At module load it runs `matchToCatalog(store.products, LOOKS)` once and maps to `Product[]`: `id` is the look number, `handle` is the entry's explicit `handle` field (kept stable independently of the title because it forms the product URL and is persisted in visitors' bags), `images` are looked up from @/lib/looks.json by look number, `variants` are the matched store product's variants passed through `orderVariants(variants, entry.sizes)` so they follow the line-sheet size run (or `[]` when the look has no match), and `price` is the first store variant's price when there is one, else the line-sheet figure. `getProducts()` returns the array in line-sheet order (jackets, then trousers, then shirts), which is the `/shop` display order; `getProduct(handle)` is a find. Both are synchronous.
- @/lib/shopify-products.ts — `StoreProduct` (`{ id, handle, title, status, variants }`, the shape the sync script writes) and `StoreMatch` (`{ productId, status, variants }`). `matchToCatalog(store, catalog)` builds two lookups over the store — by exact `handle` and by `normalize(title)` (lowercase, every non-alphanumeric run collapsed to a space, trimmed) — and for each catalog entry takes the handle hit, else the title hit; it returns `{ matched: Record<handle, StoreMatch>, unmatched: handle[] }`. Store products that match no catalog entry are dropped silently. `orderVariants(variants, sizes)` sorts a store product's variants by the look's display size run: the `sizes` string is split on commas with region suffixes (`EU`/`US`/`UK`) removed and compared case-insensitively, so `"44, 46, … 58 EU"` and `"XS, S, M, L, XL, XXL"` both work; variants whose size is not in the run rank after every listed size and keep their store order.
- @/lib/shopify-products.json — generated snapshot `{ syncedAt: ISO string | null, products: StoreProduct[] }`. Do not hand-edit; regenerate with `npm run sync:shopify` (needs the three Shopify env vars) and commit. As checked in it has been synced and holds the twelve catalog products — every one `status: 'DRAFT'` in the store — with their variants and prices, so every look is purchasable. It contains only catalog products: the sync script filters out the store's other (internal made-to-measure / bespoke) products before writing, because this repository is public.
- @/lib/shopify-admin.ts — server-only by convention (the header comment says import only from route handlers or server components; in practice only @/app/api/checkout/route.ts does). `readConfig()` returns `{ domain, clientId, clientSecret }` from `SHOPIFY_STORE_DOMAIN` / `SHOPIFY_CLIENT_ID` / `SHOPIFY_CLIENT_SECRET`, or `null` if any is unset. `accessToken` POSTs the client-credentials grant to `https://{domain}/admin/oauth/access_token` and caches `{ token, expiresAt }` in module scope, reusing it while more than 60 seconds remain (`expires_in` defaults to 3600 when absent). `adminGraphql` POSTs to `/admin/api/2026-07/graphql.json` with `X-Shopify-Access-Token` and throws on non-2xx, `errors`, or missing `data`. `createDraftOrder(config, lines, info)` runs `draftOrderCreate` with `lineItems` (`gid://shopify/ProductVariant/{variantId}`, `quantity`), `email`, a `shippingAddress` (first/last name, optional phone and address2, address1, city, `provinceCode` upper-cased when the state is exactly two characters else free-text `province`, zip, `countryCode: 'US'`), and `useCustomerDefaultAddress: false`; it returns `draftOrder.invoiceUrl` or throws `ShopifyUserError` with the joined `userErrors` messages.
- @/lib/checkout.ts — now only the `CheckoutInfo` type (email, names, phone, address1/2, city, province, zip, country) that the stepper collects and the route forwards to `createDraftOrder`.
- @/lib/looks.json — generated manifest `{ looks: [{ look, images: ['/looks/look-N/01.jpg', …] }] }`. Do not hand-edit; regenerate with `npm run import:looks -- <sourceDir>`.
- @/lib/format.ts — `formatPrice` renders `$` amounts, dropping cents for whole-dollar values.
- @/lib/gallery.ts — every non-catalog picture the app shows, as `Photo = { src, width, height }` values with real intrinsic sizes for `next/image`. `HERO_IMAGE` (`/home/hero-desktop.jpg`, landscape, lookbook frame 1345) and `HERO_IMAGE_MOBILE` (`/home/hero-mobile.jpg`, portrait, frame 1790) are hardcoded constants pointing at the hand-generated files in @/public/home, chosen from the deck's "HOMEPAGE: DESKTOP" / "HOMEPAGE: PHONE" slides. `GALLERY_IMAGES: GalleryImage[]` (`{ src, width, height, group }`) is read straight from @/lib/lookbook.json — local `/lookbook/<frame>.jpg` paths in shoot order with their output dimensions and the importer's stack `group` id. `GALLERY_STACKS = stackImages(GALLERY_IMAGES)` is the same frames folded into one entry per run of similar shots. `Season = { slug, label, title, href, stacks }` and `SEASONS: Season[]` describe the collections tabs, in chronological order (current season last): `season-2` (label "SEASON 2", `href: '/collections'`, `stacks: GALLERY_STACKS`) followed by `season-1` (label "SEASON 1", `href: '/collections/season-1'`, `stacks: stackImages(season1.images)` from @/lib/lookbook-season-1.json). `label` is the tab text, `title` feeds the archived route's page title ("Season 1 Collection"), and `href` is where the tab links — the current season's is the bare `/collections`. `NEWSLETTER_IMAGE: Photo` is resolved from `GALLERY_IMAGES` (the current shoot) at module load: the entry whose `src` ends in `/1012.jpg` (the deck's "NEWSLETTER" slide), else the first portrait frame, else the first frame — so dropping frame 1012 from a re-import degrades gracefully rather than breaking the modal.
- @/lib/lookbook.json and @/lib/lookbook-season-1.json — generated manifests, both `{ images: [{ src, width, height, group }] }`. Do not hand-edit; regenerate the current shoot with `npm run import:lookbook -- <folder>` (defaults: `--out lookbook --manifest lib/lookbook.json`) and the archived season with `node scripts/import-lookbook.mjs <folder> --out lookbook-season-1 --manifest lib/lookbook-season-1.json`. `--out` is both the folder under `public/` and the URL prefix written into `src`; the importer wipes only that folder, so re-importing one season never touches the other's files. Season 1's source folder was the previous editorial gallery's originals, downloaded once from the Shopify CDN in page order and named `0001…` so the frame-number logic applies unchanged. The importer walks its source folder recursively, keeps one file per 4-digit frame number (largest file wins when a frame was exported twice), EXIF-rotates and downscales with sharp to fit inside a max box without enlarging, wipes stale output, and records each JPEG's final dimensions. Frames are mixed portrait and landscape. After writing each output it also computes a small greyscale signature (`SIGNATURE_SIZE` square) and, walking frames in order, assigns `group` ids: a new group starts when the camera frame number jumps by `GROUP_FRAME_GAP` (10) or more, the mean pixel distance to the previous frame exceeds `GROUP_MAX_DISTANCE` (0.2), the orientation flips between portrait and landscape, or the group already holds `GROUP_MAX_SIZE` (6) frames. Signatures are used only during import and are not written to the manifest; the process is deterministic and re-runnable.
- @/lib/gallery-layout.ts — `GALLERY_COLUMNS` (the wide-screen column count, exported from lib because Next page modules may only export route fields) plus two pure, unit-tested helpers. `stackImages(images)` folds consecutive `GalleryImage`s sharing a `group` into `GalleryStack = { width, height, images[] }`, sized by the stack's first frame; only *adjacent* equal groups merge, so shoot order is preserved and a group id reappearing later would form a separate stack. `balanceColumns(items, count)` is generic over anything with `width`/`height` (`Sized`): shortest-column-first distribution into `count` columns, returning `Placed<T> = { item, index, scale }` where `index` is the source position and `scale` (≤ 1) is the per-column factor that equalises column heights. `stackImages` is consumed by @/lib/gallery.ts (once per season), `GALLERY_COLUMNS` and `balanceColumns` by both collections routes in @/app/collections.
- @/lib/validation.ts — `Validator = (value) => string | null` (message or valid). `required(message)` trims and checks non-empty; `email` tests against `EMAIL_RE` from @/lib/format.ts; `phone` requires at least seven digits after stripping non-digits; `optionalPhone` applies `phone` only when the value is non-empty; `none` always passes. Message copy for email/phone is fixed here; `required` takes its message from the caller.

### Things to Know

- Handles are fixed slug-style handles (e.g. `tuxedo-jacket-in-black-barathea`) shaped like Shopify's own handle generation, and they are the first matching key in `matchToCatalog`. The title fallback exists because the merchant's store handles do not always equal ours; a store title only has to agree with the catalog title after lowercasing and stripping punctuation.
- Purchasability is a property of the committed snapshot, not of the catalog source: `npm run sync:shopify` has been run and committed, so all twelve looks currently carry `variants` (and show the store's price) without any edit to `LOOKS`; re-running the sync is how that changes. Variant `id`s are Shopify's numeric variant ids (GIDs flattened by the sync script), which is what the cart (@/components/CartContext.tsx) keys on and what `createDraftOrder` re-wraps as `gid://shopify/ProductVariant/{id}`.
- The Shopify credentials are three server-side env vars (`SHOPIFY_STORE_DOMAIN`, `SHOPIFY_CLIENT_ID`, `SHOPIFY_CLIENT_SECRET`) from the merchant's Dev Dashboard app; they live in Vercel env and the gitignored `.env.local`. @/lib/shopify-admin.ts must never be imported from a client component or a page bundle — the secret would ship to the browser. The catalog itself never touches credentials; it only reads the committed JSON.
- The token cache in @/lib/shopify-admin.ts is module-level and survives across requests within one server process (and across tests within one Vitest file), so consumers cannot assume every `createDraftOrder` call performs a token exchange.
- Draft orders can be paid for products that are not published to the Online Store channel, which is the reason for this path. This was confirmed live: a test draft order for a `DRAFT`-status product produced a working Shopify payment page (Shop Pay, Google Pay, cards; shipping and tax calculated). Discount codes are not applied automatically on the invoice page.
- The sync script (@/scripts/sync-shopify.mjs) is the only writer of @/lib/shopify-products.json. It loads `.env.local` itself (without overriding already-set env), exits non-zero naming any missing variable, and exports `fetchAdminToken`, `fetchAllProducts`, `PRODUCTS_QUERY`, `catalogEntries`, and `keepCatalogProducts` so tests can drive it with an injected `fetch` and plain data. `catalogEntries(source)` regex-reads `{ handle, title }` pairs from the text of @/lib/catalog.ts (so the script needs no TypeScript toolchain), and `keepCatalogProducts(products, entries)` keeps a store product only when its handle or normalised title matches an entry — the same normalisation `matchToCatalog` uses. The run logs how many store products belong to the catalog and any catalog handle with no store product. Only catalog products are ever written to the JSON, which is what keeps internal made-to-measure / bespoke pricing out of this public repository. The API version (`2026-07`) is pinned separately in the script and in @/lib/shopify-admin.ts.
- The hero `Photo` dimensions are not derived from the files: they are literals in @/lib/gallery.ts that must be kept in step with the JPEGs in @/public/home, which have no import script (they were downscaled once with sharp from the LOOKBOOK originals). @/tests/hero.test.tsx checks existence and orientation, not exact pixel size.
- Editing copy happens in @/lib/catalog.ts; editing photos happens by re-running the import script, which wipes and rewrites @/public/looks and @/lib/looks.json. The catalog test in @/tests/catalog.test.ts asserts every manifest path exists on disk, so the two must be committed together. The same holds for each season's manifest and folder (@/lib/lookbook.json ↔ @/public/lookbook, @/lib/lookbook-season-1.json ↔ @/public/lookbook-season-1), checked per season by @/tests/collections.test.tsx, which also asserts no season has zero stacks.
- `EMAIL_RE` is shared: @/lib/format.ts owns it and @/lib/validation.ts imports it, so the checkout, appointment, and newsletter forms all accept the same email shape.
- Stack membership is decided at import time, not in the app: the grouping thresholds (`GROUP_FRAME_GAP`, `GROUP_MAX_DISTANCE`, `GROUP_MAX_SIZE`, `SIGNATURE_SIZE`) live in @/scripts/import-lookbook.mjs, and re-running the importer for a season recomputes every `group` id in that season's manifest along with its images. Changing how frames stack means editing the script and re-importing, not editing the manifest.
- `GALLERY_IMAGES`, `GALLERY_STACKS`, and `NEWSLETTER_IMAGE` still refer only to the current shoot; the archived season is reachable exclusively through `SEASONS`. "Current" is positional (`CURRENT_SEASON` is the last `SEASONS` entry), so adding a new season means appending it to the array and its predecessor becomes an archived `/collections/<slug>` route without further changes in @/app.
- @/lib/gallery.ts imports `stackImages` from @/lib/gallery-layout.ts, which imports the `GalleryImage` type back from @/lib/gallery.ts. The reverse edge is `import type`, erased at compile time, so there is no runtime circular evaluation.
