# Noridoc: haitch

Path: @/

### Overview

A redesigned storefront for HAITCH (haitch-usa.com), a NYC menswear label. Next.js App Router (v16) with TypeScript strict mode, CSS Modules, and npm; deployed to Vercel with zero config. There is no database. The product catalog is a static, in-repo line sheet (@/lib/catalog.ts) with studio photography committed under @/public/looks, the `/collections` gallery is split into seasons — the current LOOKBOOK shoot ("Season 2") committed under @/public/lookbook and the previous editorial gallery ("Season 1") under @/public/lookbook-season-1, each with its own generated manifest in @/lib — and the landing hero photos are committed under @/public/home. Purchasable variants come from a committed snapshot of the merchant's Shopify products (@/lib/shopify-products.json, written by `npm run sync:shopify`), and payment happens on a Shopify-hosted page reached by creating a draft order through the Shopify Admin API from the `/api/checkout` route handler. Two sibling route handlers carry the site's forms: `/api/newsletter` adds a signup to the store's Shopify customer list with marketing consent, and `/api/appointment` files a booking request on a Shopify customer record as a dated note plus an `appointment-request` tag, which is how the showroom finds it in Shopify admin. Shopify's Admin API is the only external service the site's *server* code reaches at runtime, and none of the forms talks to a third-party host from the browser. Two things do leave the browser for other hosts: Vercel Web Analytics — `<Analytics />` from `@vercel/analytics/next`, mounted in @/app/layout.tsx, which reports page views to the Vercel platform with no env vars once Web Analytics is enabled in the Vercel dashboard — and Shopify Analytics, which the browser reports to through `@shopify/hydrogen-react` (`sendShopifyAnalytics`) so that sessions, page views, product views, and add-to-carts on this site appear alongside orders in the Shopify admin. That path is @/lib/shopify-analytics.ts plus the @/components/ShopifyAnalytics.tsx and @/components/ProductView.tsx client components, configured entirely by four public `NEXT_PUBLIC_SHOPIFY_*` variables and silent when any of them is missing.

- Catalog data is hand-transcribed from the brand's "Website 2.0 Outline" line sheet into @/lib/catalog.ts, one entry per photographed "Look". Images are local files under @/public/looks, listed in the generated manifest @/lib/looks.json. At module load the catalog joins @/lib/shopify-products.json to its looks with `matchToCatalog` (@/lib/shopify-products.ts) — by handle first, then by normalised title — to pick up each look's Shopify variant ids, sizes, prices, and availability. Nothing about the catalog is fetched at build or request time, so `/shop` and `/products/[handle]` are fully static; the store snapshot is a committed file like the image manifests.
- The store's products are not published to the Online Store sales channel, so the public storefront endpoints and Shopify's `/cart/…` permalinks do not work for them. Payment therefore goes through the Admin API instead: the custom @/app/checkout page collects Bag → Information → Shipping and then POSTs the bag and contact details to @/app/api/checkout/route.ts, which first checks every bag line against the committed snapshot with `unavailableLines` (@/lib/shopify-products.ts) — answering 409 without contacting Shopify when a variant is unknown or `available: false` — then calls `createDraftOrder` in @/lib/shopify-admin.ts (`draftOrderCreate` mutation) and returns the draft order's `invoiceUrl`; the browser is sent to that Shopify-hosted payment page. A fully custom payment page is impossible under Shopify policy, so this hand-off is where Shop Pay, wallets, and cards live.
- Every Shopify caller authenticates the same way: a client-credentials token exchange (`POST /admin/oauth/access_token` with `grant_type=client_credentials`) using the merchant's Dev Dashboard app ("HAITCH website"). @/scripts/sync-shopify.mjs does it once per run; @/lib/shopify-admin.ts caches the short-lived token in module scope with its expiry and serves both runtime callers. The client secret exists only in server-side env (Vercel env, mirrored into the gitignored `.env.local`) and is never bundled for the browser — @/lib/shopify-admin.ts is imported only from the three route handlers under @/app/api (`/api/checkout`, `/api/newsletter`, `/api/appointment`).
- The appointment and newsletter forms submit to same-origin route handlers rather than to a third party from the browser. @/components/NewsletterModal.tsx POSTs `{ name, email }` to @/app/api/newsletter/route.ts, which calls `subscribeToNewsletter` in @/lib/shopify-admin.ts: it looks the address up with the Admin GraphQL `customers` query and then either updates marketing consent on the existing customer (`customerEmailMarketingConsentUpdate`) or creates one (`customerCreate` with the name split into first/last), both with `{ marketingState: 'SUBSCRIBED', marketingOptInLevel: 'SINGLE_OPT_IN' }` — so the mailing list *is* the store's Customers list, segmentable in Shopify by email marketing status. @/components/AppointmentForm.tsx POSTs `{ name, email, phone, message }` to @/app/api/appointment/route.ts, which calls `recordAppointmentRequest` in the same module: it looks the address up the same way and either appends a dated note entry to the existing customer (`customerUpdate`) and tags them (`tagsAdd`), or creates the customer (`customerCreate`) with the entry as its note and the tag already set. The tag is `appointment-request` (`APPOINTMENT_TAG`), so the showroom finds requests by filtering Customers on that tag in Shopify admin, and repeat requests from one person stack in the note under their own timestamps. An appointment request sets no marketing consent. Both forms therefore write to the store's Customers list; the site sends no email. Both forms previously POSTed straight from the browser to Formspree using `NEXT_PUBLIC_FORMSPREE_ID`, a variable that was never set in production, so every submission had been failing; the variable and the Formspree dependency no longer exist.
- All editorial imagery is local and goes through Next's built-in image optimizer: look photos (@/public/looks), the two collection seasons (@/public/lookbook for the current shoot, @/public/lookbook-season-1 for the archived one) and the newsletter picture (from the current shoot), and the landing hero (@/public/home). @/lib/gallery.ts exports each non-catalog picture as a `Photo = { src, width, height }` so pages can pass true intrinsic sizes to `next/image`, and exports the seasons as `SEASONS`, in chronological order (current season last). No route passes a custom `loader`; the only `remotePatterns` entry in @/next.config.ts (`cdn.shopify.com`) exists for legacy bag lines, not for anything the app renders today.
- The two hero photos (desktop landscape frame 1345, mobile black-and-white portrait frame 1790, both picked from the brand's "Website 2.0 Outline" deck) were downscaled once with sharp and committed under @/public/home. The desktop file comes from a brand-supplied edit of frame 1345 (`homepage_photo.jpg`, a very large master) rather than the raw LOOKBOOK export, downscaled to the same 3200×2560 the `HERO_IMAGE` constant declares; the mobile file is still from the LOOKBOOK original. There is no import script for them; if the frames change they are regenerated by hand and the `Photo` dimensions in @/lib/gallery.ts updated to match.
- Brand assets sit beside the photography and are likewise hand-generated, not scripted. The HAITCH logotype is Founders Grotesk Medium (Klim Type Foundry), supplied by the brand as an OTF and served statically from @/public/fonts; @/app/globals.css declares it with a plain `@font-face` and exposes it as the `--font-wordmark` token (falling back to the Helvetica Neue stack), and the only consumer is the nav wordmark in @/components/Nav.module.css — every other piece of type stays on `--font-primary` (Helvetica Neue). `next/font` was deliberately not used so the face can be referenced from plain CSS and from tests. The share image (@/app/opengraph-image.png) and favicon (@/app/icon.png) are both cut from the brand's logo artwork — a transparent GIF of the wordmark — with sharp: the OG image places the whole wordmark on a 1200×630 white canvas, the icon crops the "H" onto a white square. Neither is a rendered text string, so a wordmark change means regenerating both by hand.
- Three offline scripts in @/scripts commit files the app reads at build time: `import-looks.mjs` (`npm run import:looks -- <sourceDir>`) turns the `Look N/` product folders into @/public/looks + @/lib/looks.json, `import-lookbook.mjs` (`npm run import:lookbook -- <folder>`) turns a season's photo folder into `public/<out>/` + a manifest (one image per unique frame number, with recorded width/height and a `group` id marking runs of near-identical frames, which the collections pages show as single tap-to-cycle tiles) — by default @/public/lookbook + @/lib/lookbook.json for the current shoot, or `--out lookbook-season-1 --manifest lib/lookbook-season-1.json` for the archived season, so re-importing one season leaves the other's folder untouched — and `sync-shopify.mjs` (`npm run sync:shopify`) pages through the Admin GraphQL `products` query, keeps only the store products that belong to the catalog, and writes @/lib/shopify-products.json. The filter exists because this repository is public while the store also holds internal made-to-measure / bespoke category products whose pricing must not be committed: the script reads the `handle`/`title` pairs out of @/lib/catalog.ts source with a regex (`catalogEntries`) and keeps a store product only when its handle or normalised title matches one (`keepCatalogProducts`), logging "N of M store products belong to the catalog" and naming any catalog entry with no store product.
- Every form (appointment, newsletter, checkout information/shipping) validates inline with the shared validators in @/lib/validation.ts and the @/components/FieldError.tsx message component, so field-level error copy and accessibility wiring are uniform across surfaces.
- Storefront activity is reported to Shopify Analytics from the browser, separately from the Admin API paths above and from Vercel Web Analytics. @/lib/shopify-analytics.ts wraps the analytics pieces of `@shopify/hydrogen-react` (Shopify's official headless utilities; nothing else from the package is used): `readAnalyticsConfig()` reads `NEXT_PUBLIC_SHOPIFY_SHOP_ID`, `NEXT_PUBLIC_SHOPIFY_STOREFRONT_TOKEN`, `NEXT_PUBLIC_SHOPIFY_CHECKOUT_DOMAIN`, and `NEXT_PUBLIC_SHOPIFY_COOKIE_DOMAIN` and returns `null` if any is absent, in which case every tracker is a no-op. @/components/ShopifyAnalytics.tsx (mounted once in @/app/layout.tsx after `<Analytics />`) keeps Shopify's `_shopify_y`/`_shopify_s` visitor cookies on the shared top-level domain via `useShopifyCookies` and sends a `PAGE_VIEW` on every route change; @/components/ProductView.tsx sends a `PRODUCT_VIEW` from `/products/[handle]`; and `CartProvider.add` in @/components/CartContext.tsx sends an `ADD_TO_CART`. Every event is posted with `sendShopifyAnalytics(event, checkoutDomain)` — under the store's own domain, so the visitor cookies carry through to the Shopify-hosted checkout — and identifies the store as `gid://shopify/Shop/<id>` and products as `gid://shopify/Product/<id>` from the new `Product.storeId` (the matched snapshot's product id, set in @/lib/catalog.ts). There is no consent banner: `hasUserConsent` is fixed to `true` because the store sells in the US only and the cookies are first-party.

### Core Implementation

| Layer | Location | Role |
|---|---|---|
| Routes | @/app | Pages, layouts (the root layout also mounts Vercel's `<Analytics />` and the Shopify `<ShopifyAnalytics />` reporter), metadata — including `/collections` (current season) and `/collections/[season]` (archived seasons) — and the route handlers under `/api`: `checkout` (Shopify draft order), `newsletter` (Shopify customer + marketing consent), `appointment` (Shopify customer note + `appointment-request` tag); the only server code that reaches an external service at runtime |
| UI | @/components | Client/server components incl. cart state (`CartContext`, whose `add` also reports to Shopify Analytics), the render-nothing Shopify Analytics reporters (`ShopifyAnalytics` for cookies and page views, `ProductView` for product views), and the collections gallery: `SeasonTabs` (season switcher), `GalleryGrid` (balanced columns + viewer state), `GalleryStack` (tap-to-cycle / tap-to-expand tile), `GalleryViewer` (full-screen dialog with a hover magnifier, shared with the product page's `ProductGallery`); the product page's `ProductDetails` disclosure and `SizeGuide` drawer (garment-measurement tables with an inch/cm toggle) |
| Data & utilities | @/lib | Static catalog (line-sheet copy + prices, joined to the Shopify snapshot for variants and `storeId`) + `Product` types, store-snapshot matcher, server-only Shopify Admin client (token + `draftOrderCreate` + `subscribeToNewsletter` + `recordAppointmentRequest`), browser-side Shopify Analytics reporter (`shopify-analytics.ts`: config from `NEXT_PUBLIC_` vars, `PAGE_VIEW` / `PRODUCT_VIEW` / `ADD_TO_CART` payload builders), `CheckoutInfo` type, price format, the size guide's garment charts (`SIZE_CHARTS`) with inch/cm formatting, hero / newsletter `Photo` entries + one lookbook manifest per season folded into `SEASONS` (each with its stacks), column balancing (`GALLERY_COLUMNS`, `balanceColumns`), form field validators |
| Offline scripts | @/scripts | `import-looks.mjs` (product looks → @/public/looks + @/lib/looks.json), `import-lookbook.mjs` (a season's photos → `public/<out>/` + a manifest; defaults to @/public/lookbook + @/lib/lookbook.json), `sync-shopify.mjs` (Admin API → @/lib/shopify-products.json) |
| Tests | @/tests | Vitest + React Testing Library, configured by @/vitest.config.ts and @/vitest.setup.ts |

Cart ("bag") state lives in `localStorage` under the key `haitch-bag`, exposed to React via `useSyncExternalStore` in @/components/CartContext.tsx — the server always renders an empty bag and the real contents appear right after hydration, avoiding SSR mismatch. Bag lines are keyed by Shopify `variantId`, which is what `/api/checkout` turns into `gid://shopify/ProductVariant/{id}` line items.

Design references per surface: The Row (nav), Rick Owens (shop grid, checkout stepper), YSL (product page, bag drawer), Phoebe Philo (appointment form), Emily Dawn Long (footer).

### Things to Know

- @/AGENTS.md (aliased by @/CLAUDE.md) warns that this Next.js version differs from training data and points to guides under `node_modules/next/dist/docs/`.
- The canonical site URL is `https://haitch-usa.com`: @/app/layout.tsx sets it as `metadataBase`, which is what turns the relative `opengraph-image.png` / `icon.png` file conventions into the absolute URLs social scrapers need. It was set ahead of the DNS move, so a preview deployment still advertises the production host in its share metadata.
- Founders Grotesk is a licensed commercial typeface. The OTF in @/public/fonts is served to every visitor as a web font, which requires a web-font licence from Klim; holding that licence is the brand's responsibility, not something the repo enforces.
- Environment variables come in two groups. The three server-side Shopify values `SHOPIFY_STORE_DOMAIN` (the `*.myshopify.com` host), `SHOPIFY_CLIENT_ID`, and `SHOPIFY_CLIENT_SECRET` are read by the sync script and by all three route handlers; none is `NEXT_PUBLIC_`, so nothing about where the forms go ships in the browser bundle. The four `NEXT_PUBLIC_SHOPIFY_*` values — `SHOP_ID` (the numeric shop id), `STOREFRONT_TOKEN` (a public Storefront API access token created through the Admin API and titled "HAITCH website analytics"), `CHECKOUT_DOMAIN` (the store's primary domain, `shop.haitch-usa.com`), and `COOKIE_DOMAIN` (`haitch-usa.com`) — are deliberately public: Next inlines them into the browser bundle at build time (so changing one takes a redeploy), only @/lib/shopify-analytics.ts reads them, and they grant no write capability. Both groups live in Vercel's project env and are pulled into the gitignored `.env.local` for local runs; the sync script reads `.env.local` itself, the route handlers and the analytics module read `process.env`. Every route answers 503 when any server-side Shopify value is missing, the sync script exits with the missing names, and analytics silently sends nothing when any public value is missing. The client secret must never be committed or pasted anywhere. `NEXT_PUBLIC_FORMSPREE_ID`, `RESEND_API_KEY`, `APPOINTMENT_TO`, and `APPOINTMENT_FROM` no longer exist — the appointment route used to email the showroom through Resend and now writes to Shopify instead, so no email provider is configured anywhere.
- There are two analytics integrations, mounted side by side after the `CartProvider` tree in @/app/layout.tsx. Vercel Web Analytics (`<Analytics />` from `@vercel/analytics`) injects Vercel's collection script — `/_vercel/insights/script.js` on the site's own origin in production, a debug build from `va.vercel-scripts.com` in development — and records page views once Web Analytics is switched on for the project in the Vercel dashboard (Analytics tab); it needs no env var and no event call anywhere. Shopify Analytics (`<ShopifyAnalytics />`, @/components/ShopifyAnalytics.tsx, over @/lib/shopify-analytics.ts) is the one that carries configuration and explicit events: it is what makes this headless site's traffic visible in the Shopify admin next to the orders the draft-order checkout produces, reported as the `headless` sales channel. On `/products/*` the layout component sends nothing and the page's `ProductView` sends a `PRODUCT_VIEW` instead, since Shopify counts a product view as the page view; every other route gets a `PAGE_VIEW` with a `pageType` of `home`, `collection` (`/shop`), `cart` (`/checkout`), or `page`. Send failures are caught and logged as `[shopify-analytics] event not sent:` and never reach the UI.
- The size guide shows the brand's real garment measurements, not generic conversions: `SIZE_CHARTS` in @/lib/sizing.ts transcribes the "SIZE CHARTS" slide of the Website 2.0 Outline deck in inches (Jacket 44–58, Trouser 29–36, Shirts XS–XXL) and @/components/SizeGuide.tsx renders it in inches (quarter fractions) or rounded centimetres. The trouser chart is keyed by waist inches 29–36 exactly as the deck writes it, while the trousers themselves are sold in the EU 44–58 run (`TAILORED_SIZES` in @/lib/catalog.ts), so those two axes do not correspond one-to-one. The product page no longer prints a `SIZES: …` line; the size run is visible only as the `AddToCart` options.
- The Shopify app needs the `write_customers` scope (added by the merchant) for both `/api/newsletter` and `/api/appointment`; without it the customer mutations return `userErrors` and the route answers 502 with Shopify's message. @/components/AppointmentForm.tsx and @/components/NewsletterModal.tsx only check `res.ok`, so the customer sees the form's generic error state either way. The appointment path was verified live: a test request appended a tagged note to an existing customer record in the store.
- The site does not read Shopify product data at request time; the only runtime Shopify calls from the server are the checkout draft order and the two form routes' customer writes (the browser additionally posts analytics events to Shopify, which read nothing back). Product/variant/price/availability data is the committed snapshot @/lib/shopify-products.json: whenever store products, variants, prices, or stock change, run `npm run sync:shopify` and commit the JSON (then redeploy). Availability everywhere — the SOLD OUT tile on `/shop` (@/components/ProductGrid.tsx), the disabled sizes in `AddToCart`, and the 409 stock guard in `/api/checkout` — is as of the last sync, not live inventory; the guard reads the same committed file the pages were built from. Shopify itself does not refuse a draft order for an out-of-stock variant, which is why the route checks the snapshot before creating one. The committed snapshot has been synced: it holds the twelve catalog products (all `status: DRAFT` in the store) with their variants and prices, so every look carries `variants`, `AddToCart` mounts on every product page, and the bag/checkout flow is reachable for all twelve looks. If the file were ever regenerated against a store with no matching products it would fall back to `products: []`, hiding `AddToCart` while line-sheet prices still show.
- Store products are matched to looks by handle first, then by title normalised to lowercase alphanumerics (@/lib/shopify-products.ts); store products with no catalog entry are dropped twice — by the sync script before they reach the committed JSON, and again by `matchToCatalog` at build time — and unmatched looks simply stay unpurchasable. A matched look's variants are re-ordered by its line-sheet size run with `orderVariants` (the store returned tailoring sizes reversed and shirt sizes scrambled), and its displayed `price` is the first store variant's price after that ordering, falling back to the line-sheet figure.
- The route handlers under @/app/api (`/api/checkout`, `/api/newsletter`, `/api/appointment`) are the only dynamic routes; every page is static. Draft-order checkout works for products that are not published to the Online Store channel, which is why it replaced cart permalinks; this was verified live — a test draft order for a `DRAFT`-status product produced a working Shopify payment page (Shop Pay, Google Pay, cards, with shipping and tax calculated). Discount codes are not applied automatically on the resulting invoice page.
- Node 25 ships a broken methodless global `localStorage` that shadows jsdom's under Vitest; @/vitest.setup.ts installs an in-memory `Storage` polyfill so cart tests exercise the real Storage API.
- The `@/` import alias maps to the repo root in both @/tsconfig.json and @/vitest.config.ts.
- `cdn.shopify.com` (`/s/files/**`) is the only `remotePatterns` entry and stays because bag lines persisted in visitors' `localStorage` before the catalog switch may still reference legacy Shopify product images. Nothing the app renders today (hero, looks, lookbook, newsletter) references the Shopify CDN.
- Generated manifests (@/lib/looks.json, @/lib/lookbook.json, @/lib/lookbook-season-1.json) and their image folders must be committed together: tests assert every manifest path exists on disk, for every season. The same applies to the hand-made hero files: @/tests/hero.test.tsx asserts both exist under @/public/home with the expected orientations.
- Which lookbook frames collapse into one collections tile is decided offline, not in the app: @/scripts/import-lookbook.mjs assigns the `group` ids in each season's manifest from frame-number gaps, a greyscale pixel-distance threshold, orientation flips, and a maximum run length. Re-running the importer recomputes that season's stacks along with its images; the app only folds *consecutive* equal `group` values (`stackImages` in @/lib/gallery-layout.ts).
- Look photos are shown two ways from one `Product.images` list: @/components/ProductGallery.tsx scrolls them at the importer's fixed 4:5, and clicking one opens the same @/components/GalleryViewer.tsx the collections gallery uses — its props are a `Photo[]` plus a spoken `label`, so it knows nothing about lookbooks or products — with a cursor-following 2× magnifier on hover-capable pointers only. Which shoot frames a product shows, and in what order, is set per product with the optional `frames` list (1-based frame numbers in display order) in @/lib/catalog.ts — omit it to show every frame as shot — never by editing @/lib/looks.json or deleting from @/public/looks. The line-sheet detail lists on the product page are behind a closed-by-default MORE DETAILS disclosure (@/components/ProductDetails.tsx).
- Seasons are an ordered list, not a lookup table: `SEASONS` in @/lib/gallery.ts is in chronological order (current season last), `CURRENT_SEASON` (the last `SEASONS` entry) is what `/collections` renders, and `ARCHIVED_SEASONS` is what `/collections/[season]` pre-renders via `generateStaticParams` (unknown slugs 404). `GALLERY_IMAGES`, `GALLERY_STACKS`, and `NEWSLETTER_IMAGE` continue to mean the *current* shoot. Season 1's frames are the previous site's editorial gallery — the Shopify-CDN photos that were the gallery before the lookbook import — downloaded once in their original page order, numbered `0001…`, and run through the same importer, so both seasons share the `{ src, width, height, group }` manifest shape and the same `GalleryGrid`/`GalleryStack`/`GalleryViewer` components.
