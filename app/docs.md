# Noridoc: app

Path: @/app

### Overview

Next.js App Router routes for the storefront: the hero landing page, shop grid, product detail pages, the editorial collections gallery (current season at `/collections`, archived seasons at `/collections/[season]`), appointment booking, about, contact, and the custom checkout stepper, plus the route handlers under `/api`: `checkout` creates a Shopify draft order for the bag, `newsletter` adds a signup to the store's Shopify customer list with marketing consent, and `appointment` files a booking request on a Shopify customer record as a dated, tagged note. Pages are thin — they read data from @/lib and compose components from @/components, with styling in colocated CSS Modules plus @/app/globals.css.

### How it fits into the larger codebase

@/app/layout.tsx is the composition root: it wraps every page in `CartProvider` (from @/components/CartContext.tsx) and mounts the global `Nav`, `Footer`, and `BagDrawer`, so cart state is available on every route; outside the provider, as the last children of `<body>`, it renders Vercel's `<Analytics />` (`@vercel/analytics/next`), the only script in the app that reports to a service other than Shopify, and then `<ShopifyAnalytics />` (@/components/ShopifyAnalytics.tsx), which keeps Shopify's visitor cookies on the shared cookie domain and reports a `PAGE_VIEW` per route change to Shopify Analytics through @/lib/shopify-analytics.ts. Catalog-driven pages (`/shop`, `/products/[handle]`) call the synchronous `getProducts`/`getProduct` from @/lib/catalog.ts; image-driven pages read from @/lib/gallery.ts — `/` takes the local `HERO_IMAGE`/`HERO_IMAGE_MOBILE` `Photo` objects (`{ src, width, height }` pointing at @/public/home), while the collections routes take `SEASONS` — one entry per season, each carrying its `stacks` (that season's manifest, `{ src, width, height, group }` per frame generated by @/scripts/import-lookbook.mjs, folded by `stackImages` in @/lib/gallery-layout.ts so consecutive near-identical frames become one tile). `/collections` renders `CURRENT_SEASON` (the last `SEASONS` entry) and `/collections/[season]` renders a matching archived season; both mount @/components/SeasonTabs.tsx above the grid and hand `balanceColumns(season.stacks, GALLERY_COLUMNS)` to the client component @/components/GalleryGrid.tsx, which renders each tile as a @/components/GalleryStack.tsx and opens @/components/GalleryViewer.tsx full screen. That same viewer is what `/products/[handle]` opens when a look photo is clicked, through @/components/ProductGallery.tsx. `/checkout` renders @/components/CheckoutFlow.tsx, whose PAYMENT step POSTs the bag to `/api/checkout`; `/appointment` renders @/components/AppointmentForm.tsx, which POSTs to `/api/appointment`; and the footer's @/components/NewsletterModal.tsx (mounted by the layout on every page) POSTs to `/api/newsletter`. The three route handlers under @/app/api are the only places in the app that import the server-only Shopify Admin client @/lib/shopify-admin.ts (`createDraftOrder`, `subscribeToNewsletter`, and `recordAppointmentRequest` respectively, each behind `readConfig`); the two form routes also import `EMAIL_RE` from @/lib/format.ts to re-check the address server-side.

```
CheckoutFlow (client) ── POST { lines, info } ──▶ app/api/checkout/route.ts
                                                    │ readConfig()  → 503 if env missing
                                                    │ parseLines()  → 400 if bag empty/invalid or no email
                                                    │ unavailableLines(lines, snapshot) (lib/shopify-products.ts)
                                                    │     → 409 { error } if any variant is unknown / sold out
                                                    │       (no Shopify call)
                                                    │ createDraftOrder() (lib/shopify-admin.ts)
                                                    │     → 502 { error } on Shopify failure (logged)
                                                    ▼
                    window.location.assign(url) ◀── 200 { url: invoiceUrl }

NewsletterModal (client) ── POST { name, email } ──▶ app/api/newsletter/route.ts
                                                    │ readConfig()  → 503 if Shopify env missing
                                                    │ name empty or email fails EMAIL_RE → 400 (no Shopify call)
                                                    │ subscribeToNewsletter() (lib/shopify-admin.ts)
                                                    │     customers(query) → customerEmailMarketingConsentUpdate | customerCreate
                                                    │     → 502 { error } on ShopifyUserError / transport failure (logged)
                                                    ▼
                           status 'sent' ◀── 200 { ok: true }

AppointmentForm (client) ── POST { name, email, phone, message } ──▶ app/api/appointment/route.ts
                                                    │ readConfig()  → 503 if Shopify env missing
                                                    │ name/message empty or email fails EMAIL_RE → 400 (no Shopify call)
                                                    │ recordAppointmentRequest() (lib/shopify-admin.ts)
                                                    │     customers(query) → customerUpdate(note) + tagsAdd | customerCreate(note, tags)
                                                    │     → 502 { error } on ShopifyUserError / transport failure (logged)
                                                    ▼
                           status 'sent' ◀── 200 { ok: true }
```

### Core Implementation

| Route | Rendering | Notes |
|---|---|---|
| `/` | Static | Full-bleed hero `<picture>`: `getImageProps` is called twice with the same alt/`priority`/`sizes: '100vw'` and each `Photo` spread in (`{ ...common, ...HERO_IMAGE }`), the mobile call contributing only its `srcSet` to a `(max-width: 767px)` `<source>` and the desktop call supplying the `<img>` props; no custom loader. SHOP THE COLLECTION link |
| `/shop` | Static | Renders `ProductGrid` over `getProducts()` in line-sheet order (jackets, trousers, shirts) (4-across, hover image swap); a look whose every snapshot variant is unavailable renders as a dimmed SOLD OUT tile |
| `/products/[handle]` | SSG via sync `generateStaticParams` | `notFound()` on unknown handle; mounts the render-nothing client component @/components/ProductView.tsx first, which reports a Shopify `PRODUCT_VIEW` for the product; `ProductGallery` scroll column (each photo opens the full-screen `GalleryViewer`, which magnifies under a hovering mouse) + sticky purchase panel — price, `AddToCart` size selector, `SizeGuide` drawer trigger, description — whose detail lists sit behind a `ProductDetails` disclosure; the panel is capped at the viewport height below the nav and scrolls internally (scrollbar hidden) when its content is taller |
| `/collections` | Static shell | Server component for the current collection (`CURRENT_SEASON` (the last `SEASONS` entry), "Collection 2"): `<SeasonTabs active={current.slug} />` then `<GalleryGrid columns={balanceColumns(current.stacks, GALLERY_COLUMNS)} />` (both helpers from @/lib/gallery-layout.ts). The client `GalleryGrid` renders each stack as a `GalleryStack` tile (one visible frame; tapping a multi-frame tile cycles it, tapping a lone frame opens it full screen) and owns the `GalleryViewer` dialog. Tile wrappers carry `--ratio`/`--scale` CSS vars and `order`; the first three tiles load their first frame eagerly |
| `/collections/[season]` | SSG via sync `generateStaticParams` over `ARCHIVED_SEASONS` | Archived collections (currently `collection-1`). `generateMetadata` titles the page with the entry's `title` as-is (e.g. "Collection 1" — not suffixed with "Collection", which would read "Collection 1 Collection"); an unknown slug calls `notFound()`. Renders the same `SeasonTabs` + `GalleryGrid` pair as `/collections` with that collection's stacks, so tile, viewer, reveal, and parallax behaviour are identical across collections |
| `/appointment` | Static shell | Renders client `AppointmentForm`, which submits to `/api/appointment` |
| `/about`, `/contact` | Static | Brand copy / contact info |
| `/checkout` | Static shell | Renders client `CheckoutFlow`; all state is client-side |
| `/api/checkout` | Dynamic (`POST`) | Validates the body, refuses (409) a bag holding a variant the committed snapshot cannot sell, otherwise creates a draft order via @/lib/shopify-admin.ts and returns `{ url }` |
| `/api/newsletter` | Dynamic (`POST`) | `{ name, email }` → Shopify customer with email marketing consent via `subscribeToNewsletter` in @/lib/shopify-admin.ts (creates the customer, or updates consent on an existing one); returns `{ ok: true }` |
| `/api/appointment` | Dynamic (`POST`) | `{ name, email, phone, message }` → a dated note entry plus the `appointment-request` tag on the customer's Shopify record via `recordAppointmentRequest` in @/lib/shopify-admin.ts (creates the customer, or appends to an existing one's note); returns `{ ok: true }` |

The product panel in @/app/products/[handle]/page.tsx is driven by what the catalog entry carries: the price line renders only when `product.price` is defined, `AddToCart` renders only when `product.variants.length > 0`, `SizeGuide` (@/components/SizeGuide.tsx, the garment-measurement drawer) follows, then the description, and — when the entry has detail groups — @/components/ProductDetails.tsx, a MORE DETAILS disclosure button (closed by default) that mounts each `ProductDetailGroup` as an `h3` plus `<ul>` only while open. There is no separate `SIZES: …` text line: the size run appears only as the `AddToCart` `<option>`s, and `Product.sizes` is otherwise used just to order those variants. Every committed look carries a line-sheet `price`, so the panel always shows title, price, size guide, description, the MORE DETAILS toggle, and the appointment/service links; `AddToCart` appears for exactly the looks that @/lib/catalog.ts matched to a product in the committed Shopify snapshot (@/lib/shopify-products.json) — currently all twelve, since the sync has been run and committed — with its size options in line-sheet order (`orderVariants` in @/lib/shopify-products.ts).

`/api/checkout` (@/app/api/checkout/route.ts) accepts `{ lines: [{ variantId, quantity }], info: CheckoutInfo }`. `parseLines` coerces each line with `Number` and rejects the whole body unless every `variantId` and `quantity` is a positive integer and the array is non-empty; `info.email` is also required. The parsed lines then go through `unavailableLines(lines, store.products)` from @/lib/shopify-products.ts against the imported @/lib/shopify-products.json: if any bag `variantId` is missing from the snapshot or marked `available: false`, the route answers 409 `{ error: 'One or more items in your bag are no longer available.' }` and never contacts Shopify. On success it responds `{ url }` with the draft order's `invoiceUrl`. Any thrown error from the Shopify client (token exchange, GraphQL errors, or `ShopifyUserError` from `userErrors`) is logged as `[checkout] draft order failed:` and returned as 502 `{ error: message }`.

`/api/newsletter` (@/app/api/newsletter/route.ts) accepts `{ name, email }`. Both are coerced to trimmed strings (non-strings become `''`); an empty name or an email that fails `EMAIL_RE` (@/lib/format.ts) is a 400 `{ error: 'A name and a valid email address are required.' }` before any Shopify call. It then awaits `subscribeToNewsletter(config, name, email)` from @/lib/shopify-admin.ts — which looks the address up and either re-subscribes the existing customer or creates a new one — and answers `{ ok: true }`. Errors are logged as `[newsletter] subscription failed:` and returned as 502 `{ error: message }`, so a `ShopifyUserError` (for instance a missing `write_customers` scope) reaches the log with Shopify's wording.

`/api/appointment` (@/app/api/appointment/route.ts) accepts `{ name, email, phone, message }`. `readConfig()` runs first, so a missing Shopify variable is a 503 `{ error: 'Store is not configured.' }` before the body is read. `parse` trims each value (non-strings become `''`) and returns `null` — a 400 `{ error: 'Name, a valid email address and a message are required.' }` — when name or message is empty or the email fails `EMAIL_RE`; phone is optional. It then awaits `recordAppointmentRequest(config, enquiry)` from @/lib/shopify-admin.ts, which builds a note entry (`Appointment request — YYYY-MM-DD HH:MM UTC`, `Phone: …` or `—`, a blank line, the message) and either appends it to the existing customer's note and adds the `appointment-request` tag, or creates a new customer carrying the entry and the tag; the route then answers `{ ok: true }`. Errors are logged as `[appointment] request not recorded:` and returned as 502 `{ error: message }`. The route sends no email: the showroom finds requests by filtering Customers on the tag in Shopify admin.

Metadata uses the root template `%s — HAITCH`; each page exports its own `title` (or, for `/collections/[season]`, a `generateMetadata` that derives it from the season). `params` on the product and season pages is a Promise (Next 16 convention) and is awaited. @/app/layout.tsx also sets `metadataBase` to `https://haitch-usa.com`, the site's canonical host, and this folder holds the two file-convention metadata assets Next picks up automatically: @/app/opengraph-image.png (1200×630, with its alt text in @/app/opengraph-image.alt.txt) and @/app/icon.png (the favicon). Both are static PNGs derived from the brand's logo artwork — the OG image is the wordmark centred on a white canvas, the icon is the logo's "H" cropped onto a white square — generated once with sharp and committed; they are not rendered from text at build time, so they are regenerated by hand whenever the artwork changes.

@/app/globals.css is the one global stylesheet: it declares the `@font-face` for Founders Grotesk (the brand logotype, `font-weight: 500`, `font-display: swap`, loaded from @/public/fonts) and the design tokens on `:root`, including `--font-primary` (the Helvetica Neue stack every page and component inherits through `body`) and `--font-wordmark` (Founders Grotesk with the same stack as fallback). Only the nav wordmark in @/components/Nav.module.css reads `--font-wordmark`; nothing under @/app does.

### Things to Know

- There is no ISR anywhere on catalog routes: the catalog and the store snapshot are in-repo, so `export const revalidate` was removed and both pages build fully static. Adding a look means editing @/lib/catalog.ts (and re-running the import script for photos); changing what is purchasable means re-running `npm run sync:shopify` and committing @/lib/shopify-products.json; either way, redeploy.
- The route handlers under @/app/api are the only dynamic routes in the app. All three read `SHOPIFY_STORE_DOMAIN`, `SHOPIFY_CLIENT_ID`, and `SHOPIFY_CLIENT_SECRET` from `process.env` through `readConfig()` and answer 503 (`Store is not configured for checkout.` for checkout, `Store is not configured.` for the two forms) when any is missing. A deployment without the env therefore still builds and serves every page — only the PAYMENT step and the two forms fail, each with its component's inline error state.
- All three routes are thin adapters that validate the request shape (400) before any outbound call. For checkout the stock guard (409) also happens here, while the token exchange, GraphQL transport, and the `draftOrderCreate` / `subscribeToNewsletter` / `recordAppointmentRequest` input mapping live in @/lib/shopify-admin.ts, so the appointment route knows nothing about notes or tags beyond the function name. The Shopify client secret is only ever read inside these server paths — none of the forms' destinations is a `NEXT_PUBLIC_` value; the only `NEXT_PUBLIC_` variables in the app are the four Shopify analytics settings read by @/lib/shopify-analytics.ts, which grant nothing.
- The form routes' status codes are for logs, not for the customer: @/components/AppointmentForm.tsx and @/components/NewsletterModal.tsx set `sent` or `error` from `res.ok` alone and never read the body, so a 400, 502 (a Shopify `userErrors` message, e.g. from a missing `write_customers` scope), and 503 all render the same generic error copy. Only `/api/checkout`'s 409 body is shown to a customer.
- Before these two routes existed, both forms POSTed from the browser straight to `https://formspree.io/f/{NEXT_PUBLIC_FORMSPREE_ID}`. That variable was never set in production (the code fell back to `'placeholder'`), so submissions had been failing silently; the routes replaced that path and the variable is gone.
- The stock guard is only as current as the committed snapshot: it reads @/lib/shopify-products.json, the same file the static pages were built from, so "available" means available as of the last `npm run sync:shopify`, not live inventory. Shopify does not block `draftOrderCreate` on stock, so without this check an out-of-stock variant would still produce a payable invoice. The status code matters to the client: @/components/CheckoutFlow.tsx shows the 409 body's `error` verbatim and falls back to its generic copy for every other failure.
- `/checkout` and `/appointment` pages are server components that only host client components — no data fetching happens on these routes.
- Analytics is two sibling client components at the end of `<body>` in @/app/layout.tsx, both outside `CartProvider` because neither needs the bag. `<Analytics />` (Vercel) needs no env var and no event calls: it injects Vercel's collection script (`/_vercel/insights/script.js` on the site's own origin in production; a debug build from `va.vercel-scripts.com` in development) and counts page views once Web Analytics is enabled in the Vercel dashboard's Analytics tab. `<ShopifyAnalytics />` (@/components/ShopifyAnalytics.tsx) is configured by the four public `NEXT_PUBLIC_SHOPIFY_*` variables read in @/lib/shopify-analytics.ts and does nothing when any is missing; when configured it sets the `_shopify_y`/`_shopify_s` cookies on the shared cookie domain and sends a `PAGE_VIEW` on every `usePathname` change except under `/products/`, where @/components/ProductView.tsx — rendered by @/app/products/[handle]/page.tsx — sends a `PRODUCT_VIEW` instead. The product page stays a server component: `ProductView` is a `'use client'` leaf that receives the serialisable `Product` as a prop and renders `null`. No test renders the root layout, so neither `@vercel/analytics` nor the layout-mounted `ShopifyAnalytics` loads there under Vitest; @/tests/shopify-analytics.test.tsx renders `ShopifyAnalytics` and `ProductView` directly with `@shopify/hydrogen-react` mocked.
- The product page module CSS no longer styles the detail lists: the `.details*` rules moved with their markup into @/components/ProductDetails.module.css, and the `.sizes` rule went away with the removed `SIZES:` line. The page owns the two-column layout and the sticky panel; the disclosure and the full-screen photo viewer (with its hover magnifier) are self-contained client components in @/components, so the page itself stays a server component.
- The sticky panel (`.panel` in @/app/products/[handle]/page.module.css, `position: sticky; top: var(--nav-height)`) is also its own scroll container: `max-height: calc(100svh - var(--nav-height))` with `overflow-y: auto` and a hidden scrollbar (`scrollbar-width: none` plus a `display: none` WebKit scrollbar rule). When the panel's content is taller than the viewport — typically with the MORE DETAILS disclosure open — the panel scrolls on its own instead of its lower part staying out of reach until the gallery column has been scrolled past. The gallery column's scrolling is unchanged. The ≤900px rule, where the panel becomes `position: static` under the gallery, resets `max-height: none; overflow: visible` so the panel flows with the page there.
- The old "MADE TO ORDER" note derived from a description regex is gone; the new line-sheet descriptions already end with "Made to order. 5-6 week production time."
- Every route image is a site-relative path served through Next's default image optimizer: look images (`/looks/look-N/NN.jpg`), lookbook frames (`/lookbook/NNNN.jpg` for the current season, `/lookbook-season-1/NNNN.jpg` for the archived one), and the hero (`/home/hero-desktop.jpg`, `/home/hero-mobile.jpg`). No page passes a `loader`, and no route relies on the `remotePatterns` allowlist in @/next.config.ts. `sizes` props are tuned per layout (e.g. `100vw` hero, `25vw` grid tiles, `55vw` gallery slides, `33vw` collections columns).
- The hero is two different photographs, not one image cropped twice: desktop gets a landscape colour frame and phones get a portrait black-and-white frame, so the `<picture>` swaps files at the 767px breakpoint. The intrinsic `width`/`height` that `getImageProps` uses come from the `Photo` constants in @/lib/gallery.ts and must match the committed JPEGs in @/public/home, which are hand-generated (no import script) — the desktop JPEG is currently a sharp downscale of a brand-supplied edit of the frame, not of the raw shoot export, at the same dimensions `HERO_IMAGE` declares. @/tests/hero.test.tsx checks both files exist, that desktop is landscape and mobile is portrait, and that each `<source>`/`<img>` points at the right file.
- Both collections routes balance *stacks*, not frames: each stack takes the size of its first frame, goes into the currently shortest of `GALLERY_COLUMNS` columns, and every tile in a taller column is shrunk by that column's factor through `aspect-ratio: calc(var(--ratio) / var(--scale))` on the `.item` wrapper in @/components/GalleryGrid.module.css (a small `object-fit: cover` crop inside `GalleryStack`) so all three columns end on the same line with no ragged bottom. Real aspect ratios from the manifest make this computable at build time and let the page lay out at its final height before images load. On phones (≤767px) the columns collapse with `display: contents`, tiles re-sort into shoot order through the CSS `order` property, span the full width, and use the unscaled `aspect-ratio: var(--ratio)`. Re-running `npm run import:lookbook` (with `--out`/`--manifest` for an archived season) regenerates that season's frames, manifest, and therefore the grouping its page maps over.
- The column count is `GALLERY_COLUMNS` in @/lib/gallery-layout.ts rather than a constant in the page file, because Next only allows page modules to export route fields (`metadata`, `generateStaticParams`, the default component, …); sharing it between `/collections` and `/collections/[season]` therefore means importing it from lib.
- Which collection is "current" is positional: `/collections` always renders `CURRENT_SEASON` (the last `SEASONS` entry), and `/collections/[season]` only knows `ARCHIVED_SEASONS`, so the current collection's slug is not a valid `[season]` param — `SeasonTabs` links to the current collection through its `href` of `/collections`, never `/collections/collection-2`. `SEASONS` is chronological (tabs read COLLECTION 1, COLLECTION 2); promoting a new shoot means appending to `SEASONS` in @/lib/gallery.ts, and the previous last entry becomes an archived route automatically. The folder is still named `[season]` and the data still `SEASONS` even though slugs, labels and URLs say "collection" — the rename in @/lib/gallery.ts touched only user-facing values, and there is no redirect from the earlier `/collections/season-1` URL.
- There is no CSS Module for `/collections` in this folder anymore: the grid rules (`.gallery`, `.column`, `.item`, the ≤767px collapse) moved to @/components/GalleryGrid.module.css, and gallery motion lives with the tile in @/components/GalleryStack.module.css. The tile *reveal* is no longer a CSS `view()` animation — @/components/GalleryStack.tsx flips a `revealed` state when an `IntersectionObserver` first sees the tile (fade + 32px rise over 0.9s, delay cascaded by `position % 3`), while the photo inside each tile still *drifts* on a CSS `view()` timeline where supported. Reduced-motion users get static tiles. Details in @/components/docs.md.
- Both collections pages stay server components that compute the layout at build time (`SeasonTabs` is a server component too — plain `Link`s with `aria-current` on the active season); everything interactive — each tile's current frame and reveal state, the open-viewer `{ tile, frame }` state, and the full-screen `GalleryViewer` dialog — is client-side inside @/components/GalleryGrid.tsx and its children.
