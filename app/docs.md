# Noridoc: app

Path: @/app

### Overview

Next.js App Router routes for the storefront: the hero landing page, shop grid, product detail pages, editorial collections gallery, appointment booking, about, contact, and the custom checkout stepper. Pages are thin — they read data from @/lib and compose components from @/components, with styling in colocated CSS Modules plus @/app/globals.css.

### How it fits into the larger codebase

@/app/layout.tsx is the composition root: it wraps every page in `CartProvider` (from @/components/CartContext.tsx) and mounts the global `Nav`, `Footer`, and `BagDrawer`, so cart state is available on every route. Catalog-driven pages (`/shop`, `/products/[handle]`) call the synchronous `getProducts`/`getProduct` from @/lib/catalog.ts; image-driven pages read from @/lib/gallery.ts — `/` takes the Shopify-hosted `HERO_IMAGE`/`HERO_IMAGE_MOBILE` URLs, while `/collections` takes `GALLERY_STACKS` — the local lookbook manifest (`{ src, width, height, group }` per frame, generated by @/scripts/import-lookbook.mjs) folded by `stackImages` in @/lib/gallery-layout.ts so consecutive near-identical frames become one tile — and renders each tile with the client component @/components/GalleryStack.tsx. `/checkout` renders @/components/CheckoutFlow.tsx, which ends by linking out to Shopify's hosted checkout.

### Core Implementation

| Route | Rendering | Notes |
|---|---|---|
| `/` | Static | Full-bleed hero `<picture>` (`HERO_IMAGE` / `HERO_IMAGE_MOBILE`) built with `getImageProps` and the explicit `shopifyImageLoader`; SHOP THE COLLECTION link |
| `/shop` | Static | Renders `ProductGrid` over `getProducts()` in line-sheet order (jackets, trousers, shirts) (4-across, hover image swap) |
| `/products/[handle]` | SSG via sync `generateStaticParams` | `notFound()` on unknown handle; `ProductGallery` scroll column + sticky purchase panel |
| `/collections` | Static shell | Three balanced columns over `GALLERY_STACKS` computed by `balanceColumns` in @/lib/gallery-layout.ts; each tile is a `GalleryStack` (client) showing one frame of its stack at a time and cycling on tap. Tile wrappers carry `--ratio`/`--scale` CSS vars and `order`; the first three tiles load their first frame eagerly |
| `/appointment` | Static shell | Renders client `AppointmentForm` (Formspree) |
| `/about`, `/contact` | Static | Brand copy / contact info |
| `/checkout` | Static shell | Renders client `CheckoutFlow`; all state is client-side |

The product panel in @/app/products/[handle]/page.tsx is driven by what the catalog entry carries: the price line renders only when `product.price` is defined, `AddToCart` renders only when `product.variants.length > 0`, a `SIZES: …` line shows the display-only size run, `SizeGuide` follows, then the description, and a MORE DETAILS section (`h2`) renders each `ProductDetailGroup` as an `h3` plus `<ul>`. Because no current look has variants or a price, the panel today shows title, sizes, size guide, description, details, and the appointment/service links only.

Metadata uses the root template `%s — HAITCH`; each page exports its own `title`. `params` on the product page is a Promise (Next 16 convention) and is awaited.

### Things to Know

- There is no ISR anywhere on catalog routes: the catalog is in-repo, so `export const revalidate` was removed and both pages build fully static. Adding a look means editing @/lib/catalog.ts (and re-running the import script for photos), then redeploying.
- `/checkout` and `/appointment` pages are server components that only host client components — no data fetching happens on these routes.
- The old "MADE TO ORDER" note derived from a description regex is gone; the new line-sheet descriptions already end with "Made to order. 5-6 week production time."
- Local look images (`/looks/look-N/NN.jpg`) and lookbook frames (`/lookbook/NNNN.jpg`) use Next's default image optimizer. Only the landing hero passes a `loader` (@/lib/shopify-image.ts) and is the only route image still relying on the `remotePatterns` allowlist in @/next.config.ts. `sizes` props are tuned per layout (e.g. `25vw` grid tiles, `55vw` gallery slides, `33vw` collections columns).
- `/collections` balances *stacks*, not frames: each stack takes the size of its first frame, goes into the currently shortest of three columns, and every tile in a taller column is shrunk by that column's factor through `aspect-ratio: calc(var(--ratio) / var(--scale))` on the wrapper (a small `object-fit: cover` crop inside `GalleryStack`) so all three columns end on the same line with no ragged bottom. Real aspect ratios from the manifest make this computable at build time and let the page lay out at its final height before images load. On phones (≤767px) the columns collapse with `display: contents`, tiles re-sort into shoot order through the CSS `order` property, span the full width, and use the unscaled `aspect-ratio: var(--ratio)`. Re-running `npm run import:lookbook` regenerates the frames, the manifest, and therefore the grouping the page maps over.
- Scroll reveal on `/collections` is pure CSS in @/app/collections/page.module.css: inside `@supports (animation-timeline: view())` and `prefers-reduced-motion: no-preference`, each `.item` runs the `reveal` keyframes (opacity 0→1, a 16px rise, a slight scale-up from 0.985) on a `view()` timeline over `animation-range: entry 0% entry 45%`. Browsers without scroll-driven animations, and users preferring reduced motion, get the static layout.
- The collections page stays a server component; @/components/GalleryStack.tsx is the only client component in the gallery, holding just the current-frame index for its tile.
