# Noridoc: app

Path: @/app

### Overview

Next.js App Router routes for the storefront: the hero landing page, shop grid, product detail pages, the editorial collections gallery (current season at `/collections`, archived seasons at `/collections/[season]`), appointment booking, about, contact, and the custom checkout stepper, plus one route handler, `/api/checkout`, that creates a Shopify draft order for the bag. Pages are thin — they read data from @/lib and compose components from @/components, with styling in colocated CSS Modules plus @/app/globals.css.

### How it fits into the larger codebase

@/app/layout.tsx is the composition root: it wraps every page in `CartProvider` (from @/components/CartContext.tsx) and mounts the global `Nav`, `Footer`, and `BagDrawer`, so cart state is available on every route. Catalog-driven pages (`/shop`, `/products/[handle]`) call the synchronous `getProducts`/`getProduct` from @/lib/catalog.ts; image-driven pages read from @/lib/gallery.ts — `/` takes the local `HERO_IMAGE`/`HERO_IMAGE_MOBILE` `Photo` objects (`{ src, width, height }` pointing at @/public/home), while the collections routes take `SEASONS` — one entry per season, each carrying its `stacks` (that season's manifest, `{ src, width, height, group }` per frame generated by @/scripts/import-lookbook.mjs, folded by `stackImages` in @/lib/gallery-layout.ts so consecutive near-identical frames become one tile). `/collections` renders `CURRENT_SEASON` (the last `SEASONS` entry) and `/collections/[season]` renders a matching archived season; both mount @/components/SeasonTabs.tsx above the grid and hand `balanceColumns(season.stacks, GALLERY_COLUMNS)` to the client component @/components/GalleryGrid.tsx, which renders each tile as a @/components/GalleryStack.tsx and opens @/components/GalleryViewer.tsx full screen. `/checkout` renders @/components/CheckoutFlow.tsx, whose PAYMENT step POSTs the bag to `/api/checkout`; the route handler (@/app/api/checkout/route.ts) is the only place in the app that imports the server-only Shopify Admin client @/lib/shopify-admin.ts.

```
CheckoutFlow (client) ── POST { lines, info } ──▶ app/api/checkout/route.ts
                                                    │ readConfig()  → 503 if env missing
                                                    │ parseLines()  → 400 if bag empty/invalid or no email
                                                    │ createDraftOrder() (lib/shopify-admin.ts)
                                                    │     → 502 { error } on Shopify failure (logged)
                                                    ▼
                    window.location.assign(url) ◀── 200 { url: invoiceUrl }
```

### Core Implementation

| Route | Rendering | Notes |
|---|---|---|
| `/` | Static | Full-bleed hero `<picture>`: `getImageProps` is called twice with the same alt/`priority`/`sizes: '100vw'` and each `Photo` spread in (`{ ...common, ...HERO_IMAGE }`), the mobile call contributing only its `srcSet` to a `(max-width: 767px)` `<source>` and the desktop call supplying the `<img>` props; no custom loader. SHOP THE COLLECTION link |
| `/shop` | Static | Renders `ProductGrid` over `getProducts()` in line-sheet order (jackets, trousers, shirts) (4-across, hover image swap) |
| `/products/[handle]` | SSG via sync `generateStaticParams` | `notFound()` on unknown handle; `ProductGallery` scroll column + sticky purchase panel |
| `/collections` | Static shell | Server component for the current season (`CURRENT_SEASON` (the last `SEASONS` entry), "Season 2"): `<SeasonTabs active={current.slug} />` then `<GalleryGrid columns={balanceColumns(current.stacks, GALLERY_COLUMNS)} />` (both helpers from @/lib/gallery-layout.ts). The client `GalleryGrid` renders each stack as a `GalleryStack` tile (one visible frame; tapping a multi-frame tile cycles it, tapping a lone frame opens it full screen) and owns the `GalleryViewer` dialog. Tile wrappers carry `--ratio`/`--scale` CSS vars and `order`; the first three tiles load their first frame eagerly |
| `/collections/[season]` | SSG via sync `generateStaticParams` over `ARCHIVED_SEASONS` | Archived seasons (currently `season-1`). `generateMetadata` titles the page "`{title} Collection`" (e.g. "Season 1 Collection"); an unknown slug calls `notFound()`. Renders the same `SeasonTabs` + `GalleryGrid` pair as `/collections` with that season's stacks, so tile, viewer, reveal, and parallax behaviour are identical across seasons |
| `/appointment` | Static shell | Renders client `AppointmentForm` (Formspree) |
| `/about`, `/contact` | Static | Brand copy / contact info |
| `/checkout` | Static shell | Renders client `CheckoutFlow`; all state is client-side |
| `/api/checkout` | Dynamic (`POST`) | The only server-side Shopify call: validates the body, creates a draft order via @/lib/shopify-admin.ts, returns `{ url }` |

The product panel in @/app/products/[handle]/page.tsx is driven by what the catalog entry carries: the price line renders only when `product.price` is defined, `AddToCart` renders only when `product.variants.length > 0`, a `SIZES: …` line shows the display-only size run, `SizeGuide` follows, then the description, and a MORE DETAILS section (`h2`) renders each `ProductDetailGroup` as an `h3` plus `<ul>`. Every committed look carries a line-sheet `price`, so the panel always shows title, price, sizes, size guide, description, details, and the appointment/service links; `AddToCart` appears for exactly the looks that @/lib/catalog.ts matched to a product in the committed Shopify snapshot (@/lib/shopify-products.json) — currently all twelve, since the sync has been run and committed — with its size options in line-sheet order (`orderVariants` in @/lib/shopify-products.ts).

`/api/checkout` (@/app/api/checkout/route.ts) accepts `{ lines: [{ variantId, quantity }], info: CheckoutInfo }`. `parseLines` coerces each line with `Number` and rejects the whole body unless every `variantId` and `quantity` is a positive integer and the array is non-empty; `info.email` is also required. On success it responds `{ url }` with the draft order's `invoiceUrl`. Any thrown error from the Shopify client (token exchange, GraphQL errors, or `ShopifyUserError` from `userErrors`) is logged as `[checkout] draft order failed:` and returned as 502 `{ error: message }`.

Metadata uses the root template `%s — HAITCH`; each page exports its own `title` (or, for `/collections/[season]`, a `generateMetadata` that derives it from the season). `params` on the product and season pages is a Promise (Next 16 convention) and is awaited.

### Things to Know

- There is no ISR anywhere on catalog routes: the catalog and the store snapshot are in-repo, so `export const revalidate` was removed and both pages build fully static. Adding a look means editing @/lib/catalog.ts (and re-running the import script for photos); changing what is purchasable means re-running `npm run sync:shopify` and committing @/lib/shopify-products.json; either way, redeploy.
- `/api/checkout` is the only dynamic route in the app. It reads `SHOPIFY_STORE_DOMAIN`, `SHOPIFY_CLIENT_ID`, and `SHOPIFY_CLIENT_SECRET` from `process.env` through `readConfig()` and answers 503 (`Store is not configured for checkout.`) when any is missing, so a deployment without the env still builds and serves every page — only the PAYMENT step fails, with the inline error in `CheckoutFlow`.
- The route is a thin adapter: request-shape validation happens here (400 before any Shopify call), while the token exchange, GraphQL transport, and `draftOrderCreate` input mapping live in @/lib/shopify-admin.ts. The Shopify client secret is only ever read inside this server path.
- `/checkout` and `/appointment` pages are server components that only host client components — no data fetching happens on these routes.
- The old "MADE TO ORDER" note derived from a description regex is gone; the new line-sheet descriptions already end with "Made to order. 5-6 week production time."
- Every route image is a site-relative path served through Next's default image optimizer: look images (`/looks/look-N/NN.jpg`), lookbook frames (`/lookbook/NNNN.jpg` for the current season, `/lookbook-season-1/NNNN.jpg` for the archived one), and the hero (`/home/hero-desktop.jpg`, `/home/hero-mobile.jpg`). No page passes a `loader`, and no route relies on the `remotePatterns` allowlist in @/next.config.ts. `sizes` props are tuned per layout (e.g. `100vw` hero, `25vw` grid tiles, `55vw` gallery slides, `33vw` collections columns).
- The hero is two different photographs, not one image cropped twice: desktop gets a landscape colour frame and phones get a portrait black-and-white frame, so the `<picture>` swaps files at the 767px breakpoint. The intrinsic `width`/`height` that `getImageProps` uses come from the `Photo` constants in @/lib/gallery.ts and must match the committed JPEGs in @/public/home, which are hand-generated (no import script). @/tests/hero.test.tsx checks both files exist, that desktop is landscape and mobile is portrait, and that each `<source>`/`<img>` points at the right file.
- Both collections routes balance *stacks*, not frames: each stack takes the size of its first frame, goes into the currently shortest of `GALLERY_COLUMNS` columns, and every tile in a taller column is shrunk by that column's factor through `aspect-ratio: calc(var(--ratio) / var(--scale))` on the `.item` wrapper in @/components/GalleryGrid.module.css (a small `object-fit: cover` crop inside `GalleryStack`) so all three columns end on the same line with no ragged bottom. Real aspect ratios from the manifest make this computable at build time and let the page lay out at its final height before images load. On phones (≤767px) the columns collapse with `display: contents`, tiles re-sort into shoot order through the CSS `order` property, span the full width, and use the unscaled `aspect-ratio: var(--ratio)`. Re-running `npm run import:lookbook` (with `--out`/`--manifest` for an archived season) regenerates that season's frames, manifest, and therefore the grouping its page maps over.
- The column count is `GALLERY_COLUMNS` in @/lib/gallery-layout.ts rather than a constant in the page file, because Next only allows page modules to export route fields (`metadata`, `generateStaticParams`, the default component, …); sharing it between `/collections` and `/collections/[season]` therefore means importing it from lib.
- Which season is "current" is positional: `/collections` always renders `CURRENT_SEASON` (the last `SEASONS` entry), and `/collections/[season]` only knows `ARCHIVED_SEASONS`, so the current season's slug is not a valid `[season]` param — `SeasonTabs` links to the current season through its `href` of `/collections`, never `/collections/season-2`. `SEASONS` is chronological (tabs read Season 1, Season 2); promoting a new shoot means appending to `SEASONS` in @/lib/gallery.ts, and the previous last entry becomes an archived route automatically.
- There is no CSS Module for `/collections` in this folder anymore: the grid rules (`.gallery`, `.column`, `.item`, the ≤767px collapse) moved to @/components/GalleryGrid.module.css, and gallery motion lives with the tile in @/components/GalleryStack.module.css. The tile *reveal* is no longer a CSS `view()` animation — @/components/GalleryStack.tsx flips a `revealed` state when an `IntersectionObserver` first sees the tile (fade + 32px rise over 0.9s, delay cascaded by `position % 3`), while the photo inside each tile still *drifts* on a CSS `view()` timeline where supported. Reduced-motion users get static tiles. Details in @/components/docs.md.
- Both collections pages stay server components that compute the layout at build time (`SeasonTabs` is a server component too — plain `Link`s with `aria-current` on the active season); everything interactive — each tile's current frame and reveal state, the open-viewer `{ tile, frame }` state, and the full-screen `GalleryViewer` dialog — is client-side inside @/components/GalleryGrid.tsx and its children.
