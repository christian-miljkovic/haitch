# HAITCH

Redesigned storefront for [haitch-usa.com](https://haitch-usa.com) — a NYC menswear label. Next.js 16 App Router, TypeScript, CSS Modules.

## How it works

- **Catalog** — a static, in-repo line sheet in `lib/catalog.ts`: twelve "Looks" (tailored jackets, trousers, shirts) with copy transcribed from the brand's Website 2.0 Outline. Photos live in `public/looks/look-N/` and are indexed by the generated `lib/looks.json`. Nothing is fetched from Shopify at build or request time; `/shop` and product pages are fully static.
- **Prices and purchasing** — every look carries a `price` from the line sheet (jackets, trousers, and shirts each in their own band), shown on the shop grid and product page. Purchasable variants come from a committed snapshot of the merchant's Shopify products, `lib/shopify-products.json`, written by `npm run sync:shopify` through the Shopify Admin API. At build time `lib/catalog.ts` joins that snapshot to the looks by handle (falling back to title, ignoring case and punctuation); a matched look gets the store's variants (Shopify variant ids, sizes, availability), ordered by the look's line-sheet size run rather than the store's order, and shows the first variant's price; an unmatched look keeps its line-sheet price with no add-to-cart control. A matched look whose every size is unavailable shows a dimmed SOLD OUT tile on `/shop` (`components/ProductGrid.tsx`) and a disabled add-to-cart on its page. The checked-in snapshot has been synced and holds all twelve looks (each a DRAFT-status product in the store), so every look is purchasable. Availability is as of the last sync, not live inventory — the site never reads Shopify stock at request time, and the checkout route's stock check reads the same committed file.
- **Product pages** — a vertical scroll gallery of the look's photos with an image counter (`components/ProductGallery.tsx`); clicking a photo opens it full screen in the same viewer the collections gallery uses, where hovering with a mouse magnifies 2× under the cursor (touch devices are unaffected). The sticky panel holds the price, the size selector, a SIZE GUIDE drawer and the description — there is no separate SIZES line; the size run appears only in the selector. The drawer (`components/SizeGuide.tsx`) shows the brand's own garment measurements from `lib/sizing.ts`, transcribed in inches from the Website 2.0 Outline's SIZE CHARTS slide in the slide's order — Trouser 44–58 (waist size as a plain inch label, then inseam, outseam, bottom width), Jacket 44–58 (shoulders, half waist, sleeve length, back length), Shirts XS–XXL (neck, point to point, sleeve length, back length) — with an INCH / CM toggle (inches in quarter fractions like `18 1/2`, centimetres rounded whole). The trouser chart uses the same EU 44–58 run the trousers are sold in, and its Waist Size row (28–42) reads the same under either unit because it is a size label rather than a measurement. The line-sheet Styling Details / Materials and Product Care lists are folded behind a MORE DETAILS disclosure (`components/ProductDetails.tsx`), closed by default.
- **Bag** — client-side cart in `localStorage` (`components/CartContext.tsx`), YSL-style slide-in drawer, keyed by Shopify variant id.
- **Checkout** — custom Bag → Information → Shipping → Payment steps (`/checkout`). PROCEED TO PAYMENT posts the bag and contact/shipping details to `app/api/checkout/route.ts`, which first checks every bag line against the committed snapshot (`unavailableLines` in `lib/shopify-products.ts`) and answers 409 "One or more items in your bag are no longer available." — shown verbatim in the payment step — if a variant is unknown or sold out, then creates a Shopify **draft order** through the Admin API (`lib/shopify-admin.ts`) and returns its invoice URL; the browser is sent to that Shopify-hosted payment page, where Shop Pay / shop.app, Apple Pay, Google Pay and cards appear automatically. Draft orders are used because the products are not published to the Online Store channel, so Shopify's public cart permalinks would refuse them; this was verified live, with a test draft order for a DRAFT-status product producing a working payment page (Shop Pay, Google Pay, cards, shipping and tax calculated). (Shopify does not allow custom payment pages — the hosted checkout is where Shop Pay lives.) Discount codes are not applied automatically on the invoice page.
- **Appointments / newsletter** — both forms POST to same-origin route handlers; nothing form-related in the browser talks to a third party (the only browser-to-third-party traffic is the two analytics integrations described below). The footer newsletter modal sends `{ name, email }` to `app/api/newsletter/route.ts`, which adds the address to the store's Shopify customer list with email marketing consent (`subscribeToNewsletter` in `lib/shopify-admin.ts`: it looks the email up, then either creates the customer with first/last name or updates consent on the one that already exists), so subscribers are managed in Shopify Customers rather than a separate mailing tool. The appointment form sends name, email, phone and message to `app/api/appointment/route.ts`, which files the request on the customer's Shopify record (`recordAppointmentRequest` in `lib/shopify-admin.ts`): it looks the email up, then either appends a dated entry — "Appointment request — YYYY-MM-DD HH:MM UTC", the phone, and the message — to the existing customer's note and adds the `appointment-request` tag, or creates the customer with that note and tag. An appointment sets no marketing consent, and the phone stays in the note because Shopify rejects loosely formatted numbers in the phone field. The showroom finds requests in Shopify admin by filtering Customers on the tag; repeat requests from the same person stack in the note. The site sends no email. Both routes validate the body first (400) and answer 503 when the Shopify env is missing and 502 when Shopify refuses (its `userErrors` message is logged); the forms only show a sent/error state. Every form (appointment, newsletter, checkout) validates inline: a message appears under a field once it is blurred or the user tries to advance, and advancing/submitting is blocked until the step passes (`lib/validation.ts`, `components/FieldError.tsx`).
- **Images** — everything is local and served through Next's built-in image optimizer: look photos (`public/looks`), the collections seasons (`public/lookbook` for the current LOOKBOOK shoot indexed by `lib/lookbook.json`, `public/lookbook-season-1` for the previous editorial gallery indexed by `lib/lookbook-season-1.json`, both with real dimensions), the newsletter picture (lookbook frame 1012 per the Website 2.0 Outline deck, resolved as `NEWSLETTER_IMAGE` in `lib/gallery.ts` with a portrait-frame fallback), and the landing hero (`public/home`: a landscape colour frame for desktop and a black-and-white portrait frame for phones, exported as `HERO_IMAGE` / `HERO_IMAGE_MOBILE`). The hero files were downscaled once with sharp and have no import script — the phone frame from the LOOKBOOK original, the desktop frame from a brand-supplied edit of the same shot (resized to the dimensions `HERO_IMAGE` already declared, so nothing in `lib` changed); regenerate by hand if the frames change. `cdn.shopify.com` remains in `next.config.ts` only so bags saved before the catalog switch can still show their legacy product images.
- **Brand assets** — the HAITCH logotype is Founders Grotesk Medium (Klim Type Foundry), supplied by the brand as an OTF, served from `public/fonts` and declared with a plain `@font-face` in `app/globals.css` as the `--font-wordmark` token (`next/font` is not used, so plain CSS and tests can reference it). Only the nav wordmark (`components/Nav.module.css`) uses it; all other type is Helvetica Neue via `--font-primary`. It is a licensed commercial typeface — serving it as a web font needs a web-font licence from Klim, which is the brand's responsibility. The Open Graph share image (`app/opengraph-image.png`, 1200×630) and favicon (`app/icon.png`) are cut from the brand's logo artwork with sharp — the full wordmark on white, and the "H" alone on a white square — and committed as static files; regenerate them by hand if the artwork changes. `metadataBase` in `app/layout.tsx` is `https://haitch-usa.com`, so share URLs point at the production host regardless of where a build is served.
- **Collections gallery** — organised by collection. `/collections` shows the current shoot (Collection 2) and `/collections/collection-1` the previous editorial gallery, with a small COLLECTION 1 / COLLECTION 2 tab strip above the grid (`components/SeasonTabs.tsx` — the code keeps its earlier "season" naming, including the `lookbook-season-1` folder; only labels, slugs and URLs say "collection"); the list is `SEASONS` in `lib/gallery.ts`, in chronological order (current collection last), and archived collections are pre-rendered from it. Each collection is three balanced columns of lookbook tiles (`components/GalleryGrid.tsx`, grouping and balancing from `lib/gallery-layout.ts`). Every tile is clickable: a lone frame opens a full-screen viewer; runs of near-identical frames are collapsed into one tile that cycles through its frames on tap with a crossfade and an "i — k" counter, plus a small expand control that opens the current frame full screen (`components/GalleryStack.tsx`). The viewer (`components/GalleryViewer.tsx`) steps frames with arrow keys or side controls, magnifies under the cursor on hover, and closes on Escape. Tiles rise into view as they scroll on screen and their photos drift slightly on a CSS scroll-driven timeline (both off under reduced motion); on phones the columns collapse to one in shoot order.
- **Analytics** — two integrations, both mounted at the end of `<body>` in `app/layout.tsx`. Vercel Web Analytics (`<Analytics />` from `@vercel/analytics`) injects Vercel's collection script and records page views once Web Analytics is enabled for the project in the Vercel dashboard (Analytics tab); no env var or key is involved. Shopify Analytics (`components/ShopifyAnalytics.tsx` + `lib/shopify-analytics.ts`, built on the analytics helpers of `@shopify/hydrogen-react`, Shopify's official headless utilities) reports the storefront's activity to the Shopify admin so it sits alongside the orders the draft-order checkout produces: it sets Shopify's `_shopify_y`/`_shopify_s` visitor cookies on `haitch-usa.com` (shared with the checkout on `shop.haitch-usa.com`) and sends a `PAGE_VIEW` on every route change (`home`, `collection` for `/shop`, `cart` for `/checkout`, otherwise `page`), a `PRODUCT_VIEW` from each product page (`components/ProductView.tsx`, in place of the page view), and an `ADD_TO_CART` from the bag's `add()` (`components/CartContext.tsx`) with the chosen variant and total. Events are posted under the store's own checkout domain as the `headless` sales channel in USD and name products by their Shopify ids (`Product.storeId`, taken from the committed snapshot; a look the snapshot did not match is skipped). There is no consent banner — the store sells only in the US and the cookies are first-party — so `hasUserConsent` is fixed to true. Configuration is the four public `NEXT_PUBLIC_SHOPIFY_*` variables listed under Environment; when any is missing nothing is sent, and a failed send is only logged (`[shopify-analytics]`).

## Syncing products from Shopify

```bash
npm run sync:shopify
```

`scripts/sync-shopify.mjs` reads `SHOPIFY_STORE_DOMAIN`, `SHOPIFY_CLIENT_ID`, and `SHOPIFY_CLIENT_SECRET` from the environment or `.env.local`, exchanges the client credentials for a short-lived Admin API token, pages through every product in the store with the Admin GraphQL `products` query, keeps only the products that belong to the catalog (matching each store product's handle or normalised title against the `handle`/`title` pairs read from `lib/catalog.ts`, and logging "N of M store products belong to the catalog" plus any look with no store product), and writes `lib/shopify-products.json` (`{ syncedAt, products: [{ id, handle, title, status, variants: [{ id, size, price, available }] }] }`, with Shopify GIDs flattened to numeric ids). Commit the JSON: the site reads it at build time (catalog join, SOLD OUT tiles, disabled sizes) and `/api/checkout` reads it at request time to refuse bag lines whose variant is missing or `available: false`; nothing queries Shopify for product data or stock at request time. Shopify itself does not block draft orders on stock, so this snapshot is the only thing standing between a stale bag and a payable invoice. Re-run and commit whenever store products, variants, prices, or stock change, then redeploy. Products in the store that match no look are never written to the snapshot — the repository is public and the store also carries internal made-to-measure / bespoke products whose pricing must stay out of it; looks with no store match stay unpurchasable.

## Importing look photography

```bash
npm run import:looks -- ~/path/to/High-res-Ecom   # [--width 2000] [--quality 80]
```

`scripts/import-looks.mjs` reads a folder of `Look N/` directories of high-res JPEGs, downscales each to 2000px wide with sharp (EXIF-rotated, mozjpeg, never enlarged), writes `public/looks/look-N/01.jpg…` in filename order, removes stale output, and regenerates `lib/looks.json`. Do not hand-edit the manifest. Copy (titles, sizes, descriptions, details) is edited in `lib/catalog.ts`. Which frames a product shows, and in what order, is set with `frames: [n, …]` (1-based shoot frames in display order) on that look's entry in `lib/catalog.ts` — for example the Black Plain Weave Jacket uses `[4, 1, 2, 5]` to lead with its full-length frame and skip the straight-on and walking shots, and the trousers use `[1, 2, 3, 4, 5]` to drop a crop that does not show them. Leave `frames` off to show every frame as shot. This is done in the catalog rather than by deleting files; the manifest and `public/looks` stay as the importer wrote them.

## Importing the lookbook

```bash
npm run import:lookbook -- ~/path/to/LOOKBOOK   # [--max-width 1600] [--max-height 2000] [--quality 78]
# an archived season goes to its own folder and manifest:
node scripts/import-lookbook.mjs ./season-1 --out lookbook-season-1 --manifest lib/lookbook-season-1.json
```

`scripts/import-lookbook.mjs` walks the source folder recursively (root and `BOOKLET SELECTS`, jpg and png), keeps one file per 4-digit frame number in the filename (largest file wins when a frame was exported twice), EXIF-rotates and downscales each to fit inside the max box with sharp (never enlarged), writes `public/<out>/<frame>.jpg` in frame order (`--out` defaults to `lookbook`), removes stale output from that folder only, and regenerates the manifest (`--manifest`, default `lib/lookbook.json`) with each image's `src`, `width`, `height` and a `group` id. Because `--out` is also the URL prefix and the only folder that gets wiped, several seasons coexist and re-importing one leaves the others alone. Collection 1's source was the previous site's gallery photos, downloaded once from the Shopify CDN in page order and named `0001…` so the frame-number rules apply as-is. Groups mark runs of near-identical frames: walking frames in order, a new group starts when the frame number jumps by 10 or more, a 24×24 greyscale signature differs from the previous frame by a mean pixel distance above 0.2, the orientation flips, or the group already has 6 frames. The collections pages show each group as one tap-to-cycle tile, so re-running the import for a season recomputes that season's stacks along with its images. Both committed seasons use the defaults (1600×2000 box, quality 78), which suit a three-column gallery. Do not hand-edit the manifests; the collections routes read them through `SEASONS` in `lib/gallery.ts`, and the newsletter modal reads the current shoot's manifest.

## Environment

| Variable | Purpose |
| --- | --- |
| `SHOPIFY_STORE_DOMAIN` | The store's `*.myshopify.com` host |
| `SHOPIFY_CLIENT_ID` | Client ID of the store's Dev Dashboard app ("HAITCH website") |
| `SHOPIFY_CLIENT_SECRET` | Client secret of that app — server-side only, never committed or shared |
| `NEXT_PUBLIC_SHOPIFY_SHOP_ID` | The store's numeric shop id; analytics reports it as `gid://shopify/Shop/<id>` |
| `NEXT_PUBLIC_SHOPIFY_STOREFRONT_TOKEN` | A public Storefront API access token created through the Admin API (titled "HAITCH website analytics") — not the client secret |
| `NEXT_PUBLIC_SHOPIFY_CHECKOUT_DOMAIN` | The store's primary domain, `shop.haitch-usa.com`; analytics events are posted under it |
| `NEXT_PUBLIC_SHOPIFY_COOKIE_DOMAIN` | `haitch-usa.com`; the domain Shopify's `_shopify_y`/`_shopify_s` cookies are set on so checkout sees them |

The three `SHOPIFY_*` values are read only on the server and are never `NEXT_PUBLIC_`. The four `NEXT_PUBLIC_SHOPIFY_*` values are deliberately public: Next inlines them into the browser bundle at build time (so a change needs a redeploy), only `lib/shopify-analytics.ts` reads them, and they grant no write capability; without them the site builds and runs and analytics simply sends nothing. The Shopify app needs the product read scopes for the sync, the draft-order scopes for checkout, and `write_customers` for the newsletter signup and the appointment request (both write customer records). The three values are used by `npm run sync:shopify` (offline) and by the `/api/checkout`, `/api/newsletter`, and `/api/appointment` route handlers (runtime); they are set in Vercel's project environment and pulled into the gitignored `.env.local` for local work. Without them the site still builds and every page renders, but the three routes answer 503 — the payment step, the newsletter modal, and the appointment form show an error. The forms used to post from the browser to Formspree via `NEXT_PUBLIC_FORMSPREE_ID` (never set in production, so submissions had been failing), and the appointment route then briefly emailed the showroom through Resend (`RESEND_API_KEY`, `APPOINTMENT_TO`, `APPOINTMENT_FROM`); none of those variables exists any more and no email provider is configured.

## Deploying to Vercel

Zero-config: import the repo in Vercel, set the three `SHOPIFY_*` variables and the four `NEXT_PUBLIC_SHOPIFY_*` analytics variables, deploy. Turn on Web Analytics in the project's Analytics tab to start collecting page views — the `<Analytics />` component is already in the layout. No `vercel.json` needed. Every page is static; the `/api/checkout`, `/api/newsletter`, and `/api/appointment` route handlers are the only dynamic routes.
