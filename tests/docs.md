# Noridoc: tests

Path: @/tests

### Overview

Vitest + React Testing Library suite covering the storefront's behavior: the static catalog and its image manifest, the landing hero's local photos, both photo import scripts, the Shopify sync script and store-to-catalog matcher, the collections gallery (both season routes and the season tabs) and its stack/column layout helpers against the lookbook manifests, the product page, cart/bag interactions, the checkout stepper through to its `/api/checkout` hand-off, the checkout route handler itself, the appointment and newsletter forms (including inline validation messages), and the shop grid. Run with `npm test` (or `npm run test:watch`); configuration lives in @/vitest.config.ts (jsdom environment, `@/` alias) and @/vitest.setup.ts.

### How it fits into the larger codebase

Tests exercise the real modules in @/app, @/components, @/lib, and @/scripts. Catalog-facing tests read the real in-repo catalog (@/lib/catalog.ts) and check it against files on disk under @/public/looks; the collections test does the same for every season in `SEASONS` (@/lib/lookbook.json against @/public/lookbook, @/lib/lookbook-season-1.json against @/public/lookbook-season-1), and the hero test checks the `Photo` constants in @/lib/gallery.ts against @/public/home. Cart and checkout tests use a synthetic purchasable product from @/tests/helpers/products.ts (`makePurchasableProduct`) so they do not depend on what the committed Shopify snapshot (@/lib/shopify-products.json) happens to contain. Only true externals are mocked: `next/navigation` (via `vi.mock`, since components render outside a Next router), global `fetch` (Formspree submissions, the browser's call to `/api/checkout`, and — in the route and sync tests — Shopify's token and GraphQL endpoints), `window.location` (stubbed so the payment hand-off's `assign` can be observed), the Shopify env vars (`vi.stubEnv`), and `IntersectionObserver` (absent in jsdom).

### Core Implementation

- `catalog.test.ts` asserts the catalog offers the twelve looks in look order with unique handles, that every referenced image path is site-relative and exists under `public/`, that each look has at least two images (the grid hover needs two), and that `getProduct` resolves by handle. It also pins two catalog conventions: the `frames` path in @/lib/catalog.ts — the Black Plain Weave Jacket's `images` equal its manifest entry re-ordered to `[4, 1, 2, 3, 5]` (hand-on-hip frame first) and never include the sixth walking frame, and the Black Plain Weave Trousers' `images` equal their manifest entry minus the last frame and never include `/looks/look-10/06.jpg` — and that satin appears in a product's details exactly when its handle starts with `tuxedo-`.
- `hero.test.tsx` asserts `HERO_IMAGE` and `HERO_IMAGE_MOBILE` are site-relative paths that exist under `public/`, that the desktop photo is landscape and the mobile one portrait, then renders `Home` and checks the `<picture>`'s `(max-width…)` `<source>` srcset names the mobile file while the `<img>` src names the desktop file (decoding the optimizer URL and comparing basenames), and that the SHOP THE COLLECTION link points at `/shop`.
- `import-looks.test.ts` runs the real `importLooks()` from @/scripts/import-looks.mjs against temp JPEGs generated with sharp, verifying resize dimensions, filename-order numbering, never-enlarge behavior, stale-output cleanup, dotfile filtering, and numeric look sorting in the manifest (`Look 10` after `Look 2`).
- `import-lookbook.test.ts` runs the real `importLookbook()` from @/scripts/import-lookbook.mjs against temp JPEG/PNG sources laid out like the photographer's folder (root plus a `BOOKLET SELECTS` subfolder), verifying one output per unique frame number with the largest duplicate winning, fit-inside resizing for both orientations without enlarging, dotfile filtering, stale-output cleanup, a frame-ordered manifest carrying real output dimensions and `group` ids, and the grouping rules themselves: an adjacent visually identical frame shares its predecessor's group, while a visibly different adjacent frame (a half-black composite), a frame-number gap, and an orientation change each start a new group. It also passes `outName: 'lookbook-season-1'` and checks that the output lands under `public/lookbook-season-1/`, that manifest `src` values carry that prefix, and that the default `public/lookbook/` folder — stale file included — is left untouched, so several seasons can coexist.
- `shopify-sync.test.ts` imports `fetchAdminToken`, `fetchAllProducts`, and `PRODUCTS_QUERY` from @/scripts/sync-shopify.mjs and drives them with an injected `fetch`: the token exchange must POST `grant_type=client_credentials` with the client id/secret to `/admin/oauth/access_token` and return `access_token`, and a non-OK response must throw with the store's error text; the product read must follow `pageInfo.endCursor` across pages, send the token header and `PRODUCTS_QUERY`, and flatten `gid://shopify/…` ids to numbers with variants as `{ id, size, price: Number, available }`. It also covers `matchToCatalog` from @/lib/shopify-products.ts — handle match first, then title match ignoring case/punctuation, unmatched catalog handles reported, foreign store products ignored — and `orderVariants`: variants follow the look's size run (numeric EU runs and letter runs alike) and sizes the run does not list are appended after it; and `unavailableLines` against a two-variant fixture store: an available variant passes, a variant marked `available: false` is returned, and a variant id the store does not know is returned the same way. The snapshot-filtering half of the script is covered too: `catalogEntries` reads the twelve `{ handle, title }` entries from the real @/lib/catalog.ts source, and `keepCatalogProducts` drops store products that belong to no catalog entry.
- `checkout-route.test.ts` calls the exported `POST` from @/app/api/checkout/route.ts with real `Request` objects under stubbed Shopify env. Its bag uses a real variant id — the first `available: true` variant found in the committed @/lib/shopify-products.json — so the route's stock guard lets the order through. It asserts the success path sends `draftOrderCreate` with `gid://shopify/ProductVariant/{id}` line items, the email, and a shipping address carrying `provinceCode`/`countryCode: 'US'`, and returns `{ url }`; that an empty bag is a 400 without any Shopify call; that `userErrors` become a 502 whose `error` contains Shopify's message; that a missing env var is a 503 without any fetch; and that a bag line for a variant id unknown to the snapshot is a 409 whose `error` matches "no longer available", again with no fetch at all.
- `collections.test.tsx` asserts every `GALLERY_IMAGES` entry exists under `public/` with no repeated `src`, then renders the `/collections` page and checks exactly one visible `img` per `GALLERY_STACKS` entry (each stack's first frame); that clicking a multi-frame tile advances to the next frame, updates the button's accessible name ("frame i of k"), and wraps back to the first; that a lone-frame tile is a button ("… View full screen") which opens the `GalleryViewer` dialog on that photo, that the viewer offers no Next control for a single frame, and that Escape closes it; and that a stacked tile's expand control ("View lookbook image N full screen") opens the viewer, Next advances, ArrowLeft steps back and wraps to the last frame, and Close dismisses it. A seasons block then asserts `SEASONS` is `['season-2', 'season-1']`, that every season has at least one stack and every frame of every season exists under `public/`; that `/collections` opens on Season 2 (its tab `aria-current="page"`) with a Season 1 tab linking to `/collections/season-1`; and that the Season 1 route — the async `SeasonPage` awaited with `params: Promise.resolve({ season: 'season-1' })` — marks its own tab current, links Season 2 back to `/collections`, and renders one visible `img` per season-1 stack starting with the first stack's first frame.
- `gallery-layout.test.ts` covers `stackImages` (adjacent equal groups merge in order, a stack is sized by its first frame, the real lookbook collapses to fewer than half as many tiles while `flatMap` of the stacks still equals `GALLERY_IMAGES`) and the generic `balanceColumns` over both a synthetic mixed-orientation list and the real `GALLERY_STACKS` (every item placed once, per-column order kept, equal rendered heights, `scale` never above 1 and above a floor).
- Form tests (`appointment`, `newsletter`, `checkout-flow`) drive invalid input through blur and through pressing NEXT / SUBSCRIBE / CONTINUE, asserting the input gains an accessible description (`toHaveAccessibleDescription`) with the exact message and that the mocked `fetch` is not called / the step does not advance. `newsletter.test.tsx` additionally asserts the dialog's image `src` (decoded) contains `NEWSLETTER_IMAGE.src` from @/lib/gallery.ts, so the modal is tied to the lib-resolved frame rather than to any hardcoded path. `checkout-flow.test.tsx` also walks a filled-in bag to the PAYMENT step and asserts that PROCEED TO PAYMENT POSTs `/api/checkout` with `lines: [{ variantId, quantity }]` and the entered `info`, then calls `window.location.assign` with the returned `url`; that a failed response shows the `role="alert"` "could not start your order" message; and that a 409 response carrying `{ error }` surfaces that server message ("no longer available") in the alert instead of the generic copy, with the button left enabled for a retry.
- `product-page.test.tsx` renders the async server component directly by awaiting `ProductPage({ params: Promise.resolve({ handle }) })`, then partially mocks `@/lib/catalog` (spreading `importOriginal`) to inject one purchasable and one unpriced fixture alongside the real catalog. This covers both panel states: price + `AddToCart` present, and both hidden. It also drives the MORE DETAILS disclosure (`aria-expanded` false → true on click, the group headings and items absent before and present after, hidden again on a second click) and the photo viewer: every slide is a "View … full screen" button, clicking the second opens a dialog named after the product showing that frame, `fireEvent.mouseMove` puts `scale(2)` in the image's inline `transform`, `mouseLeave` clears it, and Escape closes the dialog.
- Component tests render composed trees under a real `CartProvider` (e.g. `Nav` + `BagDrawer` + `AddToCart` together) and drive them with `user-event`, verifying end-to-end flows like "add to cart opens the drawer with name, size, and price" and the four-step checkout gating. `product-grid.test.tsx` renders `ProductGrid` with synthetic products and asserts the priced/unpriced tiles, and that a product whose every variant is `available: false` shows "SOLD OUT" in its tile while a purchasable neighbour does not.
- @/vitest.setup.ts registers jest-dom matchers, runs `cleanup()` and `localStorage.clear()` after each test, and — critically — installs a spec-faithful in-memory `Storage` on both `window` and `globalThis`.

### Things to Know

- The `MemoryStorage` polyfill exists because Node 25 exposes a broken methodless global `localStorage` (without `--localstorage-file`) that shadows jsdom's implementation under Vitest; without it, @/components/CartContext.tsx would silently fall into its catch-and-return-empty path in tests.
- Because cart state persists in (memory-backed) localStorage, the `afterEach` `localStorage.clear()` is what isolates cart tests from each other.
- `checkout-route.test.ts` answers the stubbed `fetch` by URL (token endpoint vs `graphql.json`) rather than by call order, because @/lib/shopify-admin.ts caches the access token in module scope: after the first test in the file obtains a token, later tests never perform the exchange, so "first call is the token, second is the mutation" would not hold. Assertions locate the mutation call with `find` on the URL for the same reason.
- No test in the suite reaches the network or reads the real Shopify env: the sync tests inject `fetch` as a parameter, the route test stubs `globalThis.fetch` and the three `SHOPIFY_*` variables (and blanks one to exercise the 503), and `vi.unstubAllGlobals()`/`vi.unstubAllEnvs()` run after each test.
- `makePurchasableProduct` marks size `S` as unavailable so the disabled-variant path is covered; tests that assert on `TEST JACKET` / `$750` depend on that helper, not on store data. The one test that does read the committed snapshot is `checkout-route.test.ts`: its `VARIANT` constant is the id of the first `available: true` variant in @/lib/shopify-products.json (a non-null assertion, so a snapshot with no available variant would make the file fail at import), because the route now refuses ids the snapshot cannot sell before it ever calls Shopify. The 409 test uses a deliberately foreign id (`999999`) for the same reason.
- Catalog tests depend on real catalog contents (titles of look 1 and 12, the tuxedo jacket's handle, sizes, and detail items). Editing copy in @/lib/catalog.ts or re-importing photos requires updating those assertions.
- Form tests assert on the exact validation copy (e.g. "Enter a valid email address."), so wording lives in one place per validator (@/lib/validation.ts or the `required(...)` call site) and changes there must be mirrored here. The payment-failure tests likewise match alert copy: the generic `CheckoutFlow` message (`/could not start your order/i`) and, for the 409 case, the route's own message (`/no longer available/i`), which is asserted in both `checkout-route.test.ts` (response body) and `checkout-flow.test.tsx` (rendered alert), so changing that string in @/app/api/checkout/route.ts means updating both.
- Both import-script tests exercise sharp for real on generated images in a temp directory, so they depend on the native sharp binary being installed.
- `next/navigation` is mocked per test file with a fixed `usePathname` return, since `Nav` highlights the active link from it; the product page test also mocks `notFound` to throw so the 404 path is observable.
- `next/image` rewrites `src` into an optimizer URL with the path percent-encoded, so `collections.test.tsx` identifies frames through a `file()` helper that decodes the attribute and extracts the frame number instead of comparing `src` strings — its regex matches both `lookbook/` and `lookbook-season-N/` prefixes so the same helper serves every season; `hero.test.tsx` and `newsletter.test.tsx` use the same decode-then-`toContain` approach. Now that the hero is local, its `src`/`srcset` go through the optimizer too, which is why the hero test compares basenames rather than full URLs. Hidden frames inside a `GalleryStack` carry `aria-hidden`, which is why `getAllByRole('img')` returns one image per tile rather than one per frame.
- The product-page test stubs `IntersectionObserver` in `beforeAll` because `ProductGallery` constructs one unconditionally for its counter (unlike `GalleryStack`, which checks for it first). It does not stub `matchMedia`: jsdom has none, and `GalleryViewer`'s `canHover()` treats a missing `matchMedia` as a fine pointer, which is what lets the magnifier assertions pass. The hover is driven with `fireEvent.mouseMove`/`mouseLeave` rather than `user-event` so the test supplies `clientX`/`clientY` directly.
- The collections test does not stub `IntersectionObserver`: `GalleryStack` reveals immediately when the API is undefined, so every tile is present and clickable under jsdom. `GalleryViewer` portals into `document.body`, which `screen` queries cover, so the dialog is found with `getByRole('dialog')`; frame assertions inside it go through the same `file()` helper.
